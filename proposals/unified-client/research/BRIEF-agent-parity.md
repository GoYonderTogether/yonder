# 任务书：默认 Agent 一比一复刻方案（E4）

## 主人原话要点（转述，按原意执行）

默认安装的 Agent 要一比一复刻「当前 pi 本体 + 这组本机插件」的完成态：
- 默认系统提示词与上下文；插件在 pi 之外补的能力；插件完整而克制的英文提示词（按许可证复制或改写）。
- todo 能力。
- 选模型规则：主人临时给的价格资料要换成云端目录、GitHub 项目、排行榜等数据源，综合成本、速度、智能、任务偏好和特长，让 Agent 自己规划。
- 「主规划者」身份：自己不下场执行，守护 todo、子 Agent、后台任务和多渠道消息，负责做计划。所有 Bot 都遵循这个身份。
- 界面信息显示，包括：
  - 底栏：↑in ↓out R W CH 60.5%/200k (auto)。
  - 子 Agent 用量、LSP Active、(provider) model • thinking。
  - 诊断告警 widget。
  - 运行中委派列表，以及无活动告警。
  - Todos 树：显示 0/31，列出前 10 项，其余显示 +N more。
- compact 节奏、自动压缩的频率与方法、CH（缓存命中）控制，从 pi 插件加本体的组合里取。

Yonder 自己的提示词也要重写，覆盖：成本控制、分派与协调、自主性、上下文控制、多渠道聊天、Yonder 自我介绍。主人认为文档强制的很多规约在败坏 Agent 能力，pi 原样就挺好。新写法讲三件事：功能怎么用、原理是什么、用户看到什么，让结论自然得出，长度自然变短。写之前先对照主人的全部要求，分清哪些由 Agent 替用户决定、哪些由用户决定或需要问用户。

## 已定决定（不要推翻，有异议写进最后一节）

1. **运行时**：Yonder 运行时是 pi-durable 加 Yonder 插件 SDK，不是 pi-coding-agent。复刻的是行为和用户可见的结果，不是照搬进程结构。
   - 对 E1 列出的「可直接依赖」的包，评估两条路：写一层 pi 扩展兼容适配，或按 SDK 改写。给出结论和判定标准，不要两条都做。
2. **提示词语言**：面向模型的提示词一律用英文，pi 风格，克制。回复用户时跟随用户的语言。
3. **字数目标**：主 Agent 系统段 5–6k token，任务会话 6–7k，飞书每轮增量 ≤3k。投递去重、提及语法等硬保证下移到代码。删除按模型追加的 `runtime.discipline`。
4. **主规划者身份**：作为所有 Bot 共用的一段。
   - E0 的 B 类写成「默认替用户拿主意」，C 类写成「什么时候问用户、怎么问」。两类都从功能和原理讲起，不写成条款清单。
   - 单人 C 端场景下「不下场执行」的含义要讲清：简单的事直接做，规模化或可以并行的事再分派。
5. **选模型**：按 E3 的路线。models.dev 作为主数据源；先在上下文里注入一张选型小表，再加 `model_route` 工具；只决定降级链的第一个模型，降级逻辑不动。价格不写死在提示词里。
6. **上下文管理只留一套**：压缩与 CH 控制在 Yonder 内核里做，不依赖外部代理。吸收 bili 的思路，即尾偏折叠和缓存断点保护；压缩节奏要在用户界面上看得见。
7. **界面显示**：落在 `apps/app`（底栏、右栏、views 槽），数据来自网关事件；TUI 保持 pi 原生界面。
