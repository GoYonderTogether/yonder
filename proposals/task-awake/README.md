# 任务期间保持唤醒：已批准实现

## 判断

归主仓库的 macOS 系统集成；不放进 ui-companion，不新增状态栏进程或图标。主服务已有任务与后台执行生命周期，macOS 宿主负责入口；系统电源控制独立于卡片插件是否启用。用户已批准实现。实际验收见 docs/status.md；方案本身不代表物理合盖测试通过。

## 唯一入口

现有右键菜单添加一项 `✓ 任务期间保持唤醒`。勾选表示策略启用，不代表当前一定正在阻止睡眠；紧邻一行不可点击的真实状态：

- 没任务：`空闲 · 允许休眠`
- 有任务并已生效：`保持唤醒 · 2 项任务`
- 授权未完成：`合盖保护未授权`
- 读取或执行失败：显示真实失败，不显示已保护
- 系统已被其他应用设置为禁止睡眠：`系统已保持唤醒`

首次开启时才说明会允许合盖继续运行、增加耗电与发热，并由用户完成系统授权。日常启动与任务开始不弹授权、不抢焦点。策略在首次授权后保持开启；用户关闭后保留选择。显示器允许正常熄灭，不保持屏幕常亮。原菜单左右键功能不变。

## 活跃工作的定义

由主服务现有运行事实决定，不唤醒模型：有进行中的模型运行、已接纳待执行输入，或尚未结束的本机后台执行工作，就持有保护。多个任务共享保护，最后一项结束、取消或失败才释放。会话仅处于打开状态、单纯等用户审批/输入、未来 cron、已结束的卡片都不算运行中的工作；如果等待审批时还有本机后台工作，则仍需保护。

接入时复用 runtime 的运行/后台/排队事实，不能只数未关闭会话、只读最后一条消息，或让模型自行上报“忙碌”。不新增模型工具与第二套任务状态机。

## 两个系统能力，界面不分裂

1. 普通空闲防休眠使用进程持有的 IOKit assertion，任务期间持有，退出自动释放；不阻止显示器休眠。
2. 用户重点要求的“无外接显示器、电池供电也合盖运行”不能用普通 assertion 冒充。需要独立评估并实现有授权的系统电源控制；现有 Yonder Helper 是用户权限的隐私授权助手，并不是可直接调用的 root 电源服务。

若采用 pmset 的全局 SleepDisabled，必须由限定功能的特权服务负责授权、持有和恢复，不能让 UI 或 Agent 运行任意 root 命令。控制期覆盖后台任务，不随菜单关闭或交互卡片收起而结束；主服务断开后要清理自身持有的保护。不能简单在任务开始写 1、结束写 0：启动前已是 1 时不能替别的应用关闭；MacToolkit 等也在写这个全局设置时，没有可靠的应用级所有权，不能宣称支持多控制器同时自动管理。该模式应明确由一个应用负责。

不采用“轻度休眠仍跑任务”的描述：普通任务执行和持续网络连接需要系统继续运行。系统电量耗尽、温度保护、用户关机与网络自身断开不属于保持唤醒能保证的范围。

## 本次实查（2026-10-23）

- MacToolkit 与 YonderStatus 都在运行。
- MacToolkit 配置 power.forceAwake 为 true；实时 pmset -g 的 SleepDisabled 为 1。
- Yonder 现有状态栏没有电源控制；现有 service.info 只有版本、PID、ready 等信息，不能作为任务忙碌判断。
- 未修改系统电源、sudoers、登录项或已安装服务，未进行真实合盖测试，未据此认定旧工具失效。

## 实现验收

- 真实模型运行、本机后台任务、并行任务：最后一项结束前不释放；取消/失败后正确释放。
- 仅有历史会话或等用户回复不占用保护；未来定时任务不让机器一直醒着。
- 无授权、用户取消授权、系统状态未知不能显示“已保护”。
- 服务异常退出和更新重启后不遗留本应用的保护；已有系统设置不会被擅自关闭。
- 实机分电池/接电，测试合盖后真实任务持续进展与输出、再开盖后的系统睡眠记录；手机热点在线只能辅助观察。
- 与 MacToolkit 的控制归属需明确后才做动态系统控制，不能两个应用互相覆盖。
