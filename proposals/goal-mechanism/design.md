# 目标与验收机制：最小设计与方案比较（决策建议，非规范）

状态：提案，待维护者决定。本文不改 `docs/`、不改代码、不改生产。引用的事实分三类标注：**【仓库】** 读自本仓库 `origin/main`；**【审计】** 读自 Jarvis 只读审计报告（`audit-jarvis.md`，数据快照 2026-10-23T03:34Z）；**【公开】** 来自带链接的公开资料；**【推测】** 我的推断，没有证据。链接未能核实的明说。

## 1. 要解决的问题

维护者观察：GPT 类模型作为日常 agent，没有目标就跑几个小时，把简单任务放大、钻牛角尖、无法收敛、过度验证。设想：收到需求后先把已有需求与新需求合并成一个"可量化、路径通畅、能完成"的目标，带验收标准，在时间/上下文提醒内完成，交付后停。

### 1.1 Jarvis 的真实循环（失败模式依据）

- 【审计 §4.3-2】候选 → 审查 → CI → 再审查 → 发版 → 启用检查 → 发现缺陷 → 再发版：10-22 17:26Z 到 22:43Z 约 5.3 小时连发 6 个版本（0.2.26102201 至 0.2.26102206），其中两个补丁版由"启用检查发现缺口"触发。
- 【审计 §4.3-1、§3.3、§1.7】后台完成 → 核对 → 追加台账 → 再派 `task_run`：全会话 200 次 `task_run`；154 次模型调用只为 `cat >>` 追加台账（$20.46，占主会话调用成本 18%）；近 48 小时 76% 的运行成本来自"后台完成回传唤醒"，其中 74% 的运行没有对外回话。
- 【审计 §4.3-3、-4】5 次完整"全部待办"对账；44% 的发给主人的消息是"仍在推进，尚无新交付"。
- 【审计 §5.1 第 6、7、8 行】AGENTS.md 中"arrange task_continue""Deliver the moment work is done""端到端上线才算完成"都没有停止条件；审计指出规则被批评后只增不减，"没有'做到什么程度可以停'的上限"。
- 【审计 §2.3】软提醒几乎无用：`maxTokens` 200000 对主会话几乎每次运行都触发（184 条，在会话里追加 355 条 runtime-note），零信息量。
- 【审计 §6】审计的结论：主因是"工作流结构 + 长会话被高频唤醒"，不是话多，也不是 thinking 档位。

两个对设计有约束力的事实：

1. 这个循环**跨越很多次运行**（每次后台完成就是一次新运行），而现有软阈值是**每次运行**计的。【仓库：`packages/core/src/runtime/limits.ts`，`state.turns`、`state.warnings` 属于单次运行】所以现有 `maxMinutes/maxTurns/maxTokens` 在结构上看不到这种循环。任何有效机制必须有跨运行的、按"目标"而不是按"运行"计的状态。
2. 现有三条软提醒的措辞都在鼓励继续：`maxMinutes`："continue as needed and report meaningful progress"；`maxTurns`："continue if work remains"；`maxTokens`："Preserve the goal and continue necessary work"。【仓库：`limits.ts` 第 37–41、139、153 行】其中"Preserve the goal"假定存在一个目标，但内核里没有任何地方保存它。

### 1.2 内核已经有的相关措辞

【仓库：`packages/core/src/prompt/content.ts`】已有"Find the real goal""Stay inside the brief""Written is not done""Report without being chased"；任务段："a goal, an owner, a scope, what done looks like, where it stands, what comes next… Small things, simply do"；委派段："hand over the goal, the materials, the limits and what done looks like"。也就是说，**基础提示词已经要求"什么算做完"，但只覆盖委派，且没有预算、没有停止规则、没有"同主题无新交付就汇总"**。Jarvis 的 owner 级 AGENTS.md 又与之相反（审计 §5.1）。【推测】基础底座的措辞不足以压过 owner 级 AGENTS.md 里更具体、更靠后的规则。

## 2. 约束（来自规范，不是我的偏好）

- 不变量 6：完成的定义交给模型；内核不追加"你确定完成了吗"轮次。D3：已"删除验收与审批"，完成由模型最终回复定义，需要时"由插件补"。
- 不变量 7：时间/轮数/tokens 阈值只提醒，不截断正常任务；显式 abort、真实协议限制、防重复空转仍生效。
- 不变量 5：不存在第二套审批或验收机制；以后要加，写成钩子插件。
- 不变量 3：插件提供能力，agent（或配置档）决定用不用。
- D46 / 14 §1：`task_continue({text})` 表示"已有授权目标的一项具体后续步骤"，不得用来循环询问是否完成或制造新授权。
- AGENTS.md 第 3、4 条：规范没写的行为不发明；不写占位功能。

推论：**任何"验收"都只能是模型自己写下并自己对照的记录，内核不判定"验收通过"**；任何"预算到期"都只能是提醒加（可选）插件钩子，内核不截断。这直接决定了下面各方案的边界。

## 4. 共同的最小原语：一个"目标"该有什么

不论哪个方案，一个目标记录只需要：

```
objective     一句话：交付什么
acceptance[]  2–5 条可对照的验收，每条能指向一个具体证据（命令输出/文件/PR 状态）
budget        wallMinutes 与/或 tokens；以及"同主题连续 N 次无新交付即停下汇总"的 stopRule
nonGoals      明确不做的邻近事项（防放大）
```

规则：新需求到来时先判断并入还是新目标；并入要重写 objective/acceptance，不是叠加。收尾 = 对照验收逐条给证据，写出结论（met / partial / blocked），列出遗留项**进入下一个目标而不是当次连环修**。

## 5. 方案比较

### P0 仅提示词

做法：在内置底座（`content.ts`）加一段约 100–150 词的目标纪律：收到需求先写下目标/验收/预算/不做什么（可写在回复里或工作区文件）；新需求合并重写；同主题连续 N 次无新交付就停下汇总一次；预算到点必须收尾并交付；验收对照证据；发现的新缺陷进下一目标。不加工具。

- 实现位置：提示词（`content.ts`，一次编译进底座）。无内核逻辑、无 SDK 改动。
- 对 GPT 类：E4 直接支持"明确停止条件与预算有效"；但 E4 也说明措辞敏感，写重了会让模型把"验收"本身当作新的无限验证对象。【推测】
- 对 Claude 类：E1 说明新模型本来就能不靠 todo 跟踪多步工作，提示词层面的目标纪律成本最低。【推测】
- token：约 150 词 ≈ 200 token 进入 system，稳定可缓存，几乎为零。
- 违反不变量？否。符合"内核最小"。
- 失败模式：
  1. **跨运行状态不存在**：模型要自己数"同主题第几次"。Jarvis 的 95 次后台唤醒每次是新运行，目标只能靠转录或台账文件找回；压缩后丢失（E6 对同类问题的报道）。【推测】
  2. **压不过 owner 级 AGENTS.md**：审计 §5.1 里 8 条规则方向相反且更具体，内核底座在 system 里排在 SOUL/AGENTS 之前。
  3. 目标写了但没人读：没有任何地方把它再次呈现给模型。
- 能否打断 Jarvis 循环：**弱**。它给了停止规则的措辞，但无计数、无再现、无到期提示。

### P1 轻量目标记录（`goal_set`，不强制）

做法：新增工具 `goal_set({objective, acceptance[], budget, stopRule?, nonGoals?})` 与 `goal_close({outcome, evidence})`（见 §6 说明为什么需要第二个动词）。目标存入会话级持久存储；一个 `placement: turn` 的上下文贡献在每个 `<turn>` 之后附一段目标摘要，并带**已用时间、自目标建立以来的唤醒次数、距上次 `goal_close`/里程碑的间隔**；预算超出时摘要变为"已超预算：汇总现状，`goal_close` 或说明为什么延长"。不强制调用。

- 实现位置：**插件**（工具 + 上下文贡献），状态放插件数据或 agent 工作区文件。不要求改内核。
- 对 GPT 类：把停止条件在**每次唤醒**时重新放到眼前，正好对应 E4 的"明确停止条件"，且克服压缩丢失问题（E6：目标若只存在于转录里会被压缩吃掉；`<turn>` 块每轮新写入，不依赖旧转录）。无公开 A/B，效果为【推测】。
- 对 Claude 类：E1 提示新模型不需要 todo 工具；一个只在用户有复杂需求时才被选用的目标工具，开销小；但 Claude 类可能干脆不调用。不强制则无害。【推测】
- token：目标首次完整呈现约 100–200 token；之后每次唤醒只带一行（约 25 token）。注意 `<turn>` 内容写入转录后不可改写（03 §5.1），所以**每轮的摘要会累积**：95 次唤醒 × 150 token ≈ 14K token 的上下文增长（约占 130K 上下文的 11%），而一行版本 ≈ 2.4K。因此设计上必须"变更时完整、平时一行"。这是估算，非实测。
- 违反不变量？不违反。验收是模型自己写、自己对照，内核不判定（符合 6、D3）；预算只是显示的提醒（符合 7）；没有第二套审批（5）；agent 选用才生效（3）。唯一需要维护者确认的是"是否把它当作 D3 的实质回退"——我认为不是：D3 删的是**内核替模型判定**，这里没有判定。
- 失败模式：
  1. 模型不调用 `goal_set`（最可能；这正是"不强制"的代价）→ 退化成 P0。
  2. 目标写得太大，验收成了新的无限验证清单；"可量化"被理解成要跑更多检查。
  3. 摘要的"超预算"提醒像现有 `maxTokens` 提醒一样被习惯性忽略（审计 §2.3 的 184 条零信息提醒是前车之鉴）。
  4. 唤醒次数与 token 累计需要内核提供数字；插件自己只能数自己被渲染了几次（见 §6 的未决项）。
- 能否打断 Jarvis 循环：**最直接的软方案**。"同主题连续 N 次无新交付"可以变成一个**有计数的显示事实**，而不是让模型自己回忆；"预算到期必须收尾"在到期后的每次唤醒都被重新摆出。但它仍只是提醒，模型可以无视。

### P2 强制：无目标不得调用有副作用的工具（`beforeTool` 钩子拦截）

做法：钩子插件在 `beforeTool` 里检查当前会话有无未关闭目标；无目标时对有副作用工具返回 `{block: "先调用 goal_set"}`。

- 实现位置：钩子插件（规范允许，04 §3.6）。内核不改。
- 对 GPT 类：能保证目标一定存在。但（1）小任务（改个字）也要先 `goal_set`，多一个来回；（2）E9：没有"强制"对"可选"的公开对照；（3）E1/E2 里两家厂商的方向是把计划类工具默认关掉。【推测】它容易让模型把"填目标表单"当成仪式，目标内容敷衍。
- 对 Claude 类：同上，且 E1 说明新模型本来不需要这类工具。【推测】
- token：每个新会话/新目标至少多一次工具往返；被拦截的调用浪费一轮；对 Jarvis 这类每次唤醒都要执行 `cat >>` 的流程，如果目标已关闭，就会在下一次唤醒时被拦在门外，需要再开一个目标——容易催生"为拦截而建的目标"。
- 违反不变量？**部分抵触精神**：不变量 3（"agent 决定用不用"）与 6（完成定义交给模型）；不变量 7 说阈值只提醒不截断，拦截虽在工具层而非阈值，但效果是限制正常工作。内置底座的任务段写的是 "Small things, simply do"，与小事也要先建目标冲突。它不违反不变量 5 的字面（写成钩子插件），所以是**维护者必须明确批准的设计选择**。
- 失败模式：目标凑数；拦截提示与模型的计划冲突造成重试循环（`repeatBlock`/`repeatStop` 会介入）；与 owner 级配置档不兼容的工具（例如 cron 触发的无人值守任务）卡住；绕过：用 `bash` 做同样的副作用（`bash` 本身要不要算"有副作用"？这是个无法干净回答的分类问题）。
- 能否打断 Jarvis 循环：**不能**。Jarvis 的每次动作都在一个"已有的、很大的目标"下（"端到端上线"）。强制建目标只保证目标存在，不保证目标有界。反过来，若把 P2 改成"预算到期后拦截有副作用工具，除非 `goal_close` 或显式延长"，倒是**最硬的打断**，但这等于内核/插件在预算处截断工作，直接抵触不变量 7，需要改规范。

### P3 复用 `task_continue` / 任务台账承载目标

做法：约定 `task_continue({text})` 的 text 里必须带"目标 / 验收 / 预算"，目标跟着续办输入传递；任务台账（Jarvis 的 `agents/main/memory/*closeout*` 文件）作为目标的存放处。

- 实现位置：提示词约定 + 已有工具；无新代码。
- 现状事实：`task_continue` 只携带一段 text，通过稳定调用身份入队为 `runtime.continuation` 输入【仓库：14 §1；`prompt/index.ts` 第 30 行】；没有结构化字段、没有会话级存储。台账是 agent 的自写文件，内核不知道它。
- 对 GPT/Claude 类：与 P0 同级，外加把目标塞进续办文字。续办只在"安排下一步"时出现，**而 Jarvis 的主要唤醒（76%）是后台完成回传，不是 `task_continue`**（审计 §1.7：`task_continue` 自续只占 4/180 次运行）。所以目标搭不上最常用的唤醒路径。
- token：续办文字变长；台账文件本身就是成本来源（审计 §3.3：84KB、493 行、基本只写不读，154 次单独调用只为追加）。把目标放进台账等于把已经被证明是浪费源的东西加重。
- 违反不变量？D46/14 §1 明确"不得拿它循环询问模型是否完成、制造新授权"；用它承载目标/预算会把它的语义扩成目标系统。不违反内核最小，但语义越界。
- 失败模式：目标随续办文字逐次改写、漂移；两个入口（续办和后台回传）状态不一致；台账继续膨胀。
- 能否打断 Jarvis 循环：**弱，且可能加重**。

### 一览

| | P0 提示词 | P1 轻量目标 | P2 强制 | P3 复用续办/台账 |
|---|---|---|---|---|
| 位置 | 提示词 | 插件（+可选提示词） | 钩子插件 | 提示词约定 |
| 内核/SDK 改动 | 无 | 无（唤醒/token 计数另议，见 §6） | 无 | 无 |
| 跨运行状态 | 无 | 有 | 有 | 无（文字漂移） |
| 每次唤醒重新呈现 | 否 | 是（一行） | 是 | 仅续办路径 |
| 新增 token | ~200 固定 | ~25/次唤醒 + 一次性 ~200 | 多一次往返 + 拦截浪费 | 续办变长 + 台账 |
| 触及不变量 | 否 | 否（验收为自记录） | 精神上抵触 3/6/7，需批准 | 扩张 14 对 `task_continue` 的定义 |
| 打断 Jarvis 循环 | 弱 | **最直接的软方案** | 不能（除非加硬截断，抵触 7） | 弱/可能加重 |
| 可逆性 | 极高 | 高（下架插件即可） | 中 | 高 |

## 6. 推荐

**推荐 P0 + P1 组合，分两步，P2 不做，P3 不做。**

### 第一步（最小、可逆、零内核改动）

1. **P0 提示词**：在 `content.ts` 的任务段增补目标纪律（约 100–150 词，写进"任务"与"汇报"之间），内容限于：开工前一句话写清目标与验收（小事免）；新需求先并入、重写，不叠加；预算与停止规则；同主题连续 N 次无新交付 → 停下汇总一次；到点收尾并对照证据交付；新发现的缺陷进下一个目标，不当次连环修。只写模型反复犯错之处，符合 03 §5.2.1 的取向。避免"thorough/verify"类措辞（E4 的 Cursor 案例）。
2. **同时校正三条软提醒的措辞**（`limits.ts`）：现在三条都说"continue"。这属于运行时提示文本改动，**需要维护者确认是否算设计变更**（它不改变阈值语义，只改措辞，但 14 §1 写了行为）。
3. **本文不涉及 Jarvis 的 AGENTS.md**（owner 配置，不在仓库）；但审计 §5.1 的第 6、7、8 行改写建议是同一件事的 owner 级对应物，建议维护者另行决定（那是 owner 配置，不在仓库）。
4. 用 §7 的 A/B 验证；不通过则回滚（只是一段文字）。

### 第二步（仅当第一步数据显示"模型不自己数、不自己停"时）

做 P1 **作为官方插件**，范围收窄到：`goal_set`、`goal_close`、一个 `placement: turn` 的贡献。状态存 agent 工作区一个小文件（`goal.json`，通过 `files` 贡献声明）。摘要"变更时完整、平时一行"。

**需要内核/SDK 的未决点（不预先实现，等维护者决定）**：
- 唤醒次数与累计 token/运行时间：`RenderContext` 目前只有 agent/profile/session/workspace/event，拿不到会话用量。插件只能自己数"被渲染几次"和自己记墙钟时间，这对 Jarvis 的"几次唤醒无交付"够用，但对 token 预算不够。若要 token 预算，需要在 `RenderContext` 增加只读用量，或让预算只用时间/唤醒数。**这是 SDK 变更，须批准；建议第一版只用墙钟时间 + 自数唤醒次数，不碰 SDK。**【我没有验证 `render` 是否对每个 `wake: run` 的输入恰好调用一次；落地前需核对。】
- `goal_close` 为什么要第二个动词：不关闭，目标永远"未完成"，下一次唤醒会继续显示；关闭是"模型自己宣布完成/阻塞/放弃"，仍是模型判定，符合不变量 6。

### 为什么不是 P2

P2 解决的是"没有目标"，而 Jarvis 的问题是"目标无界"。强制会增加每个小任务的仪式，E1/E2 显示业界在把默认计划工具关掉，E9 说明没有证据证明强制更好。它的唯一真正有牙齿的变体（预算到期后拦截）等于截断，直接抵触不变量 7。

### 为什么不是 P3

最常见的唤醒不是 `task_continue`（审计 §1.7：4/180 次），目标搭不上；而台账已经是被验证的浪费来源。

### 回答"哪种方案最能直接打断这类循环"

按失败模式拆：

| 循环 | 最有效的打断点 | 方案 |
|---|---|---|
| 候选→审查→CI→再审查→启用检查→再发版（6 个版本 5.3 小时） | 目标的 **acceptance + nonGoals + "遗留缺陷进下一目标"**：一次发版就是验收，启用检查发现的问题不再回到本目标 | P0 写规则，P1 每次唤醒重现 |
| 后台完成→核对→追加台账→再派 task_run（95 次无回话唤醒） | **stopRule（同主题连续 N 次无新交付即汇总）+ 唤醒计数显示**；以及不要为追加台账发起一整轮模型调用（这是 owner 规则问题，目标机制不能解决） | P1（计数是关键，P0 无计数） |
| 反复对账全部待办、进度类消息 | 目标本身就是"唯一待办"；进度消息只在里程碑/超预算时发 | P0 + P1 |
| UI 微步进 84 次 | 不属于目标问题，是工具/批量问题 | 都不解决 |

结论：**P1 最直接，因为它是唯一同时具备"跨运行持久"与"每次唤醒重新呈现 + 计数"的软方案**；P0 是它的文字基础，P1 单独没有 P0 的规则也无意义。但必须诚实：它仍然只是提醒，对一个被 AGENTS.md 明确要求"端到端才算完成"的模型，提醒可能被压过（【推测】）。要真正打断，要么改 owner 的 AGENTS.md，要么接受预算到期的硬措施（P2 变体），而后者需要修改不变量 7，我不建议第一版做。

## 7. A/B 验证方案（真实模型 `openai/gpt-6-luna`）

模型凭据：沿用仓库 `.yonder/` 中 Yonder 自己的 ChatGPT 登录。缺凭据则跳过并写"未测"，不用模拟。Claude 类模型**不在本验证范围内**，对它们的所有判断都是【推测】。

**条件**：A0 基线（当前提示词）；A1 = P0；A2 = P0 + P1（插件落地后）。P2 不测，除非维护者要看它的反例。

**场景**（均为真实仓库、真实命令，不造假数据；放在独立临时克隆里，不碰生产）：
1. 小任务带"诱饵"：例如"给某个 CLI 增加一个只读开关"，附近存在无关的失败测试、陈旧 TODO、文档不一致。度量放大倾向：越界改动文件数。
2. 无限验证诱饵：任务本身可交付，但任何检查都总能找到下一个小问题（例如文档间措辞差异）。度量是否按时收尾。
3. 多次唤醒循环（针对 Jarvis）：派一个会产生多个后台完成回传的任务（真实 `npm test`/构建），同时给出"每步都要对账"的 AGENTS.md 压力（复制审计 §5.1 的第 6、7 行作为 owner 规则）。度量同主题无交付的唤醒次数。
4. 新需求并入：第一个需求进行中追加相关需求，度量是否合并重写目标。

**每个条件每个场景 n ≥ 10 次**，随机顺序，固定预算（例如墙钟 20 分钟或 1.5M token，仅作为"是否按时"的判据，**不 abort**，遵守不变量 7；超出由评测脚本事后记录）。

**指标**（均可从 `run.end`、事件账本、`pi_entries` 取得）：
- 运行时长（从首个输入到最后一个 `run.end`）、唤醒次数（`run.end` 数量）、总轮数；
- tokens 与 `usage.cost`（含 cacheRead）；
- 是否按时收尾（预算内出现面向调用方的最终回复）；
- 验收是否达成：**事先写好的确定性脚本**（场景 1 的功能测试、越界文件白名单）+ 双盲人工打分兜底；
- 次要：进度类消息条数、调用 `goal_set/goal_close` 的比例（A2）。

**统计**：报中位数与四分位距，Mann-Whitney 比较；不足 10 次不下结论；同时报"验收达成率下降"，因为收敛如果以验收变差为代价就不算赢。预先声明"成功"：时长/唤醒次数下降且验收达成率不下降超过一个事先设定的容差（由维护者定）。

**未知/风险**：luna 的单次方差可能很大；场景 3 对 owner 规则的复现是近似，不等于 Jarvis 现场；n=10 对尾部行为（偶发的 5 小时事故）没有统计力，不能证明"不再出现"。

## 8. 需要维护者决定的点

1. 是否接受"目标/验收是模型自己的记录，内核不判定"这一边界（即 P1 不算 D3 的回退）。
2. 第一步是否允许改 `content.ts`（P0）与 `limits.ts` 三条提醒措辞；后者我认为是提示文本而非阈值语义变更，但 14 §1 写了行为，请裁定是否属于设计变更。
3. 是否另行处理 Jarvis 的 owner 级 AGENTS.md（审计 §5.1 第 6、7、8 行）：这是对循环影响最大的单点，也与本机制互相作用。
4. P1 第一版的预算是否只用墙钟时间与自数唤醒次数（无 SDK 改动）；token 预算是否值得为 `RenderContext` 增加只读用量。
5. 是否接受"预算到期不拦截，只重复提醒"作为长期立场；若不接受，需要先修改不变量 7 再谈 P2 变体。

## 9. 不确定与限制

- 没有找到"强制 vs 可选计划工具"的直接对照实验（E9）；E3 只读到摘要。
- E2 的动机、E6 的 issue 细节、E8 的插件细节来自二手来源；`budget_limit.md` 原文未读到。
- 所有"对 GPT/Claude 的预期影响"除 E1、E4、E5 所述的厂商自身做法外，都是推测。
- 审计数据只覆盖 5.6 天，且 Jarvis 的行为同时受 owner 规则、模型（gpt-6-astra）与长会话成本结构影响，目标机制只能解释其中一部分。
- 我没有运行任何代码或模型；§7 是方案，不是结果。
