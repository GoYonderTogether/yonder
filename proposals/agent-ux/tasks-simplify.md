# T13：tasks 提醒取证与简化建议

## 结论

主人描述的“等待 N 分钟”提醒有明确来源：本机已安装的 `tasks` 插件 `user-wait` 时点直接发送到任务的 `origin`。账本中有飞书消息 ID 格式的成功返回，但不能据此证明用户读到。原文 O49 还指出提醒打扰、时长难理解，以及任务未被 AI 主动处理；后两点不能仅凭账本统计证明因果。

## 触发条件和路径

- 已安装版本每分钟检查一次：`active` 任务自最近非 moment/digest 账本活动超过默认 30 分钟后，向任务所属会话提交滞留提示；同一任务按上次 moment 再限频。提示要求继续、标记 blocked/waiting-user，或完成并附证据。失败也已先记录 moment，因此会在下一限频窗口继续尝试；上述 122 次都是关闭会话错误。
- `waiting-user` 且存在 `origin`：自最近进入该状态起满默认 120 分钟，并距上次同类 moment 满 120 分钟，逐任务发送。正文等待事项取最近带 `note` 的事件，否则取任务目标。`origin` 如不是有效投递引用，会返回失败；上述 49 次为此类失败。不会因这些失败自动修复 origin。
- `postCompact` 默认关闭；本窗口没有对应 moment 记录。上述统计只覆盖 tasks 账本，不涵盖 cron、其他插件、渠道自身通知或所有可能的飞书消息，不能排除其他来源。没有操作运行服务、发送测试消息或验证用户端展示。

## 删除 / 保留建议（待维护者决定）

1. **建议删除 tasks 自己周期性向主人逐条催办的默认行为**，不要仅把分钟换成小时。若需提醒，交由统一通知策略决定是否推送、合并、免打扰和可读时长；任务账本继续提供事实。先厘清现有消费者和兼容迁移，不直接删除公开契约。
2. **保留任务目标、状态、来源、验收证据及按权限查询**；保留真正需要主人决定的明确问题。Agent 应先继续可自主处理的部分，再说明唯一需要人的决策；这需要行为与真实场景验收，不能由计时器保证。
3. **建议移除或约束对已关闭会话的周期性 stall 提交**，先核实会话生命周期、后台等待和恢复责任，避免将暂时忙碌当成滞留；上述重复错误是证据，不证明所有 stall 无用。
4. **暂缓完成后压缩、留存等实验时点及尾部摘要的扩张**，无独立效益证据前不增加另一套自动提醒。`tasks_nudge`、面板和账本各有调用方与权限语义，不能仅凭本次统计断言无用或直接删除。

本报告是只读调查与建议，不修改设计规范、插件、配置、home 或服务；未做真实发送、模型行为、用户已读或全渠道端到端验证。
