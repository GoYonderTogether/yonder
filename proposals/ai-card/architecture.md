# 架构

基于 [foundation.md](foundation.md) 的倾向：用 Tinode 作底座。若最终不是 Tinode，下面"底座提供"一列要重写，"我们自己做"一列基本不变。

## 1. 构成

```text
浏览器（访客 / 用户）                  主人电脑上的 Yonder
  └ 网页应用                              └ card 插件（tinode-sdk 客户端）
    （Tinode 网页端分支 + 新页面）
        │ WebSocket / HTTP                      │ WebSocket / HTTP
        ▼                                       ▼
   Tinode 服务端：账号、会话、消息、同步、在线状态
        ▲
   名片服务（我们写，很小）：名片、资源、Agent 归属、设备授权
```

**第一版没有云端模型。** 访客聊天的对象是主人的 Agent，Agent 必须在线连接才能回答；离线时消息留在会话里，Agent 上线后按序号补收。名片页本身不依赖 Agent 在线。

## 2. 谁提供什么

| 能力 | 底座提供 | 我们自己做 |
|---|---|---|
| 账号、登录、匿名账号 | Tinode 的 `basic` 与 `anonymous` | 登录名按邮箱字符串使用，不配验证器 |
| 私聊、群聊、消息、同步、在线状态 | Tinode | — |
| 富文本、文件、转发、群管理、二维码、联系人 | Tinode 网页端组件 | — |
| 聊天界面、响应式 | Tinode 网页端 | 分支里改品牌与文案 |
| 名片：存储、预览、发布、名片页 | — | 名片服务 + 页面 4、5 |
| Agent 归属、设备授权 | — | 名片服务 + 页面 6 |
| Agent 接入 | `tinode-sdk` | card 插件 |
| 安装入口 | — | 页面 7（静态） |

## 3. 名片服务

一个独立的小服务，只管三样数据：

| 数据 | 内容 |
|---|---|
| `card` | 所属账号（人或 Agent）、草稿、已发布版本、资源 |
| `agent` | Agent 账号 ↔ 主人账号的归属 |
| `device_code` | 设备授权码、状态、过期时间、确认它的主人 |

调用方用 Tinode 的令牌证明身份，名片服务向 Tinode 校验〔具体做法待定〕。

## 4. 关键流程

**连接 Agent**

1. 插件 `login(start)`：名片服务生成授权码，返回页面 6 的链接。
2. 主人在页面 6 登录并确认，授权码变为已确认，记录确认者。
3. 插件 `poll` 到确认：在 Tinode 注册一个 Agent 账号（随机登录名和密码，只存本机），再带着授权码向名片服务登记归属。

**起草与发布名片**

1. Agent 写好 `card/`，调用 `channel-card_card_push`，名片服务保存草稿，返回页面 5 的链接。
2. 主人打开链接。浏览器已登录就直接显示，否则先登录。一键免登录需要由服务端签发主人的令牌，放后面。
3. 主人在页面 5 点发布；只有人的令牌能发布，Agent 的令牌不能。
4. Agent 自己的名片：Agent 推送草稿后给主人发一条带链接的消息，主人在页面 5 点发布。

**访客扫码**

1. 页面 4（免登录）展示名片。
2. 点"和 TA 聊天"：页面创建匿名 Tinode 账号，令牌存在浏览器，进入与该 Agent 的私聊。
3. Agent 在线则收到消息；离线则消息留在会话里，上线后补收。

**Agent 入群**：主人在群管理里把 Agent 账号加为成员；Agent 收到该群全部消息。

名片页上的在线提示需要另外获取在线状态，第一版进入会话后才显示〔待定〕。

## 5. 账号层级

层级从状态推出：

| 层级 | 推出 |
|---|---|
| 访客 | 匿名账号 |
| 普通用户 | 邮箱注册的账号 |
| 已连接 Agent | 名下有 `agent` 记录 |
| 已发布名片 | 有已发布的 `card` |

## 6. 名片

- 一个 Markdown 正文（标准 GFM，含引用、表格、图片）、附属资源、可选的展示卡片（一个 HTML 或 SVG 文件）。不自创卡片语法。
- 来源：Agent 推送，或用户在页面 5 粘贴、上传。两条路到同一份草稿。
- 名片页地址 `/u/<id>`，`<id>` 由系统分配，自定义短链放后面。
- 展示卡片放进独立源的 `sandbox` iframe，固定区域，不开 `allow-same-origin`、`allow-top-navigation`、`allow-forms`。
- 二维码编码名片页地址。名片图默认是头像、名字、一句话和二维码的固定模板；有 SVG 展示卡片时用它。HTML 展示卡片导出为图待定。

## 7. 基础边界

- **登录**：邮箱不验证、不发验证码，所以邮箱只是登录名，不公开显示，也不能找回密码。
- **渲染隔离**：用户 HTML 只在沙箱 iframe 里运行，这是托管用户 HTML 的前提。
- **不限制输入**：不加产品层的字数和频率限制，沿用 Tinode 服务端的默认配置。
- **信任模型与飞书相同**：平台账号被盗等于渠道被盗；Agent 怎么对待非主人的发送者，由它自己的绑定和配置档决定。
- **合规**：面向公众、保留记录、允许未验证邮箱注册的聊天服务，上线前必须核实适用的规定。本文不构成法律意见。
