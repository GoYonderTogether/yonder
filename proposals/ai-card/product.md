# 产品

## 1. 为什么做

- **获客入口。** BP 把开源作为采用与获客路径（[bp/THESIS.md](../../bp/THESIS.md) 16.3）。名片给社区一个看得见、扫得到、马上能体验的东西，体验之后再引向"自己装一个"。
- **补渠道的短板。** BP 押注 B4"渠道即界面"依赖渠道开放度：个人微信没有官方机器人接口（F3），飞书需要同组织。自己的聊天平台让 Agent 有一个不受别家约束的入口。
- **一个人就有价值。** 主人发一次链接就有用，不需要先有网络效应；有了账号和聊天之后，再自然长出社交。
- **与 BP 的关系。** BP 16 节已把名片撤出主线叙事，保留为未验证场景。本草案把它当获客入口，不当主营。

## 2. 最小闭环

| # | 闭环 | 验收 |
|---|---|---|
| 1 | **主人发布名片**：装插件、登录；让 Agent 起草，推到名片服务，在页面预览；点发布，得到二维码、链接、名片图 | 一个人从装插件到拿到可分享的名片，只在 Agent 对话和一个浏览器页面里完成 |
| 2 | **访客体验**：扫码，不登录就看到名片页，并和主人的 Agent 聊天；页尾有"拥有自己的 Agent"入口 | 一个没有账号的人，扫码后能聊起来；Agent 离线时消息不丢 |
| 3 | **成为用户**：邮箱注册后加好友、私聊、建群；有 Agent 的人把 Agent 拉进群，没有的人直接参与 | 一个群里同时有人和 Agent |
| 4 | **审批**：Agent 给自己起草名片，主人收到一条带链接的消息，去审核并发布 | Agent 的名片经主人点击才上线 |

闭环 1–2 是最小的拉新路径，闭环 3–4 把平台变成真正的聊天应用。

## 3. 本版的简化

- **没有云端模型。** 访客聊天的对象是主人的 Agent，Agent 必须在线连接才能回答。离线时名片页照常可看，聊天消息留着，Agent 上线后补收。
- **登录最简。** 邮箱加密码；不验证邮箱存在，不发验证码。代价：邮箱只是登录名，不公开显示，也不能找回密码，也挡不住批量注册。
- **聊天、群、好友、二维码、转发都借用底座**，不自己设计（[foundation.md](foundation.md)）。
- **页面极少。** 新增四个，其余复用（[pages.md](pages.md)）。

## 4. 账号层级

| 层级 | 怎么判断 | 能做什么 |
|---|---|---|
| 访客 | 匿名账号 | 看名片、和 Agent 聊天 |
| 普通用户 | 邮箱注册 | 加好友、私聊、建群、参与群聊、粘贴名片并发布 |
| 已连接 Agent | 名下有 Agent 账号 | 把 Agent 拉进群、和 Agent 在平台上聊天 |
| 已发布名片 | 有已上线的名片 | 被扫码、被访客聊天 |

## 5. 原则

- **平台像真正的聊天应用。** 体验以飞书、微信为准，不另造交互。
- **产品层不设限。** 不限制用户输入多少字，不限制 Agent 工具调用和转述的长度，允许 Agent 转发原始消息。
- **安全不另起一层。** 平台如实标出发送者是谁，Agent 怎么对待由 Yonder 的绑定和配置档决定。
- **能力靠接缝长，不靠预留功能。** 云 Agent、云端分身、共享、手机端都只是在现有接缝上加实现，不在第一版里写。
- **上线只能由人点。** 名片可以由 Agent 起草和推送，但上线必须是主人在页面里点击。

## 6. 本版不做

云端模型和云端 Agent、云端分身、模型额度、用户自带密钥代理、虚拟环境共享、手机 App、付费、邮箱验证与找回密码、免登录预览链接、消息推送、产品层的字数和频率限制。

## 7. 分期

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| S0 验证 | [foundation.md](foundation.md) 里的 spike，确认底座可用 | 七项验证有结论 |
| S1 | 起项目：Tinode 服务端 + 网页端分支 + 名片服务；页面 1–7；card 插件的登录、收发、`card_push` | 闭环 1、2 跑通 |
| S2 | 页面 8–10：加好友、建群、Agent 入群、审批 | 闭环 3、4 跑通 |
| 之后 | 见"本版不做" | 看 S1、S2 的使用再定 |

## 8. 成功怎么看

沿用 [BP 15.3](../../bp/THESIS.md)，不以"二维码能打开"代替需求验证：访客是否更容易理解这个人；是否形成有意义的后续联系；主人是否愿意持续分享和维护。增长漏斗：访问 → 首次提问 → 多轮对话 → 点击安装入口 → 完成安装。先量基线，不预设目标数字。

## 9. 商业

候选是平台托管订阅、将来的云端模型用量结算，对应 BP 16.3 的两条收入线。定价、成本和付费意愿都未验证，本草案不写数字。
