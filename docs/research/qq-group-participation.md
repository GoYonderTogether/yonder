# QQ 群持续参与：调研与实现草案

2026-10-21。状态：**调研完成；群普通文字消息接纳已补；周期参与、消息定向回复、父会话请求尚未实现。** 本文是供维护者审核的草案，不替代现行 spec。

## 结论

采用“全量接收 → 每群独立会话 → 程序分桶 → 模型决定是否发言 → 显式回复目标消息”。优先复用现有事件账本、write 绑定、persistent/per:conv、pi inbox 和投递。QQ 插件负责接收与时间窗口，内核补当前缺失的通用工具契约，不引入第二个 Agent 运行时。

默认只需一个群分身模型，先用真实 `openai/gpt-6-luna` 验证；同一次运行可以选择等待或发送，无须每次先调用判断模型再调用回复模型。若真实用量表明判断占比过高，再比较两段模型，不能先假定它更省。

## 1. 已核实的平台与当前实现

腾讯官方提供 `GROUP_MESSAGE_CREATE`。机器人开启“接收所有消息”后才会推送不限 @ 的消息，intent 仍是 `GROUP_AND_C2C_EVENT (1<<25)`，字段与群 @ 事件一致。[官方群全量事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html)

腾讯 SDK 1.0.4 已解析该事件，mentionGate 支持 passthrough。原首版 Yonder 适配器另有限制，只接受 `GROUP_AT_MESSAGE_CREATE`；本次解除这一限制，并在正文清理前用 SDK 标记是否 @ 自己，普通文字消息保持 mentioned=false。

现有默认 `wake: mention` 已有旁观语义：普通消息写入该群会话而不调用模型，@ 才运行。它可以满足“下一次 @ 时看到之前群聊”，尚不满足“定期自主参与”。平台开关是否已启用、普通消息是否真实收到须分别验收，不能从 SDK 支持推断现场已开通。

当前接收器仍以文字为范围；全量事件意味着“不限 @”，并不代表图片、语音等内容已经完成解析。持续参与阶段要保留这些事件的来源及类型，不能把未解析媒体当作已读正文。

## 2. 可借鉴的现成方案

| 参考 | 核实到的能力 | 对 Yonder 的取舍 |
|---|---|---|
| OpenClaw Ambient room events | 普通群消息作为安静上下文，只有模型调用 message 工具才公开发言；最终正文不自动发到群。当前文档列出的支持渠道为 Discord、Slack、Telegram | 借鉴“收消息与公开发言分离”；不能据此宣称 QQ 已有整套可直接启用的实现 |
| OpenClaw group history / collect | 待处理背景保留发送者，已进入 session 的消息不重复注入；collect 合并兼容输入，仍有来源和接纳生命周期限制 | 借鉴增量背景与批次归属；collect 不是通用的一分钟全监听功能 |
| MaiBot | Planner 可以选择等待、工具或回复；reply 工具显式接收 msg_id；消息上下文保留时间、发送者、引用关系 | 借鉴模型决定发言和消息定向；不移植其独立运行时、人格和记忆系统 |
| AstrBot group_chat_plus 社区插件 | 同群并发消息按顺序合并，区分等待窗口与多用户批次；有决策模型与回复模型两条路径 | 用来核对并发、重复处理问题；其概率、冷却与双调用路径不作为本需求默认方案 |

依据：[OpenClaw ambient room events](https://docs.openclaw.ai/channels/ambient-room-events)、[群背景](https://docs.openclaw.ai/channels/group-messages)、[collect 队列](https://docs.openclaw.ai/concepts/queue)、[MaiBot Planner](https://github.com/Mai-with-u/MaiBot/blob/5c7637e6913c84d1c3d5e742fa9e95a7e70d3501/src/maisaka/chat_loop_service.py)、[MaiBot reply 工具](https://github.com/Mai-with-u/MaiBot/blob/5c7637e6913c84d1c3d5e742fa9e95a7e70d3501/src/maisaka/builtin_tool/reply.py)、[消息 ID 与发送者格式](https://github.com/Mai-with-u/MaiBot/blob/5c7637e6913c84d1c3d5e742fa9e95a7e70d3501/src/maisaka/context/planner_messages.py)、[社区插件架构](https://github.com/Him666233/astrbot_plugin_group_chat_plus/blob/main/docs/ARCHITECTURE.md)。

MaiBot 当前还提供按新消息数量触发和估算回复概率的动态触发。这些是其自己的成本策略；本需求中程序只分桶，不用概率决定最终是否回复。[MaiBot 聊天与回复说明](https://docs.mai-mai.org/faq/chat-and-reply)

这些是一手文档和源码证据，未在本机部署、实测第三方框架。MaiBot 等仅参考行为，不复制第三方代码或引入许可证不兼容的运行组件。没有发现一个现成 QQ 插件同时覆盖本需求全部条件。

## 3. 推荐的完整流程

```mermaid
flowchart TD
  QQ[QQ 官方群事件] --> E[插件转换，事件账本去重]
  E --> W[每群 write 入独立 persistent 会话]
  W --> B[非空时间桶；@ 可提前结束等待]
  B --> R[批次事件经绑定唤醒同一群分身]
  R --> M[模型读取未读范围和已有上下文]
  M --> S[保持安静]
  M --> P[选消息 ID，显式发送]
  M --> A[请求所属 Agent 主会话协助]
  A --> H[主会话按来源与已有授权处理]
  H --> M
  P --> D[QQ 真实回执与投递事件]
```

### 接入和配置

1. 沿用现有扫码配置：Agent 输出官方链接/二维码，可打开网页；用户自行登录并绑定机器人，密钥只保存到目标 home 的凭据文件。
2. 检查平台是否能开启“接收所有消息”。若需要用户在 QQ 或管理端确认，返回准确待办；不能伪造已经具备的平台权限。
3. 同一 Agent 为每个群建立 `persistent/per:conv` 会话，使用群只读配置档；主人私聊仍走现有 main。这里的 session 是独立上下文和执行队列，不需要每群启动一个 OS 进程。
4. 默认对已获平台授权和渠道允许的群接收普通消息。接收范围沿 allowedGroups，不因为全量监听扩大原有允许范围。

### 消息进入与分桶

1. 原始消息沿 `message.in` 写入账本：真实平台 ID、群、发送者、时间、@/引用、正文或明确的媒体状态。重连重复推送沿现有核心去重。
2. 群绑定用 `wake: write` 将正文写入该群的原生 conversation，收到消息本身不调用模型。聊天正文不复制到插件自建的第二份转录。
3. 建议初始窗口为 **60 秒**，从首条未处理消息计时；没有新内容不运行。@ 可以提前结束当前等待窗口，将截至此时的上下文一起送入。这只是调度优先级，不强制模型发言。
4. QQ 插件发出有稳定身份的批次事件，经显式绑定运行同一群会话；批次只说明本次消息范围、真实 ID 和未读位置，不把已经写入 conversation 的正文再复制一次。
5. 同群同一时刻只有一次原生运行；忙时先归入后续窗口，窗口事件不能每分钟无限积压。只持有一个待处理范围，不另建模型任务队列。不同群保留各自会话。
6. 单个窗口超过真实上下文预算时，明确记录未覆盖范围。可以按顺序继续处理，或让模型按需读取剩余原文；不能静默截掉后把整批标为已读。预算策略要用真实水群数据确定。

“每分钟一批”降低的是唤醒和重复上下文开销，不会消除读正文的 token。按每窗口一次初始判断计算，持续活跃群约 60 次初始运行/小时；@ 提前处理、工具循环、续办及拆批会增加调用，不能称为 60 次模型请求硬上限。空闲群没有空桶调用。

### 已读、未读与定向回复

把三个事实分开：**已收到、已被模型覆盖、已成功回复**。不回复也可能已经读过；成功运行不代表发送成功。

- 使用账本事件顺序记录批次边界，平台消息 ID 作为外部引用，不把 QQ ID 当可比较的序号。
- 每次运行取得固定的消息范围；运行期间新收到的消息进入下一范围，不能被上一轮的已读位置一起越过。
- “已读”仅表示该内容已进入本次模型上下文并完成本次处理，不宣称模型理解正确；未送入的媒体正文、溢出内容仍未覆盖。
- 已经在原生 session 中的背景不每分钟全文重发。批次通知区分本轮未读范围、已有已读背景、机器人最近发送及其回执，便于判断是否继续同一个话题。
- 默认群批次 `reply: none`。普通最终正文保留在会话，公开群消息必须显式调用发送工具。模型可以零次、一次或多次选择目标，不必用特殊长段落解释为何沉默。
- 为通用 `message_send` 补上已有 SDK 支持的 `replyTo` 字段。内核核实目标消息属于本群与当前允许范围，再交 QQ 插件；无 message 能力仍只能发回本次群来源。
- QQ 发送时分别处理被动回复来源 `msg_id` 与显式引用 `message_reference`。SDK 已有相应接口，客户端最终引用效果必须真实验证，不能把 API 接受 msg_id 当成界面已引用。
- 来源超过 QQ 被动回复时效、额度耗尽或目标不可用，明确记录失败；不偷偷借一条新消息的 ID 发送旧回答。主动推送要满足平台自身权限与原有授权。
- 恢复沿原生接纳和运行事实核对批次。已接纳批次不重复提交；投递不明沿现有 uncertain 规则，不自动重发。

### 群分身、共享记忆与主会话协助

群分身属于同一个常驻 Agent，复用其 workspace、身份和选中的上下文；每个群的聊天上下文独立。文件与持久记忆记录默认只读，不给 write/exec/network/admin/cross-agent。

当前 Yonder 有 context-files 与手工 memory 目录，尚无长期记忆引擎。第一步应让群分身按需读取同一工作区现有记忆，而非把所有文件和私聊历史每轮灌入。其他会话的私密转录不是普通 memory 文件；需要时由主会话代查并返回适合群场景的结果。可读取记忆与可以公开这些内容是两个边界。

已经核对本机 AI-Being 的 `plugins/voice/agents/voice.md` 和 voice-sessions：它采用 permission=read、memory scope=*，复杂工作经 sessions.send 交已有父会话；内部往来不自动公开，入队也不代表完成。借鉴这种责任划分，不移植旧 Brain/Threads 存储。

Yonder 的实际缺口：`agent_ask` 需要 message 能力，并拒绝同一 Agent；群 persistent 会话也没有 task 的 parent 关系。不能用 task_run 冒充——子任务能力会与只读发起方取交集，无法请求父会话执行动作。

**待维护者决定的推荐契约：** 提供受限的 `parent_ask({text})`（草案名字），只允许非 main 的 Agent 分身向**所属 Agent 的 main 绑定**提交内部请求；不接受任意目标、会话或权限参数。由内核填写真实来源群、发送者、原消息、分身与因果关系，不能信任模型在正文里自称“主人已批准”。

该入口作为固定内部请求能力，可在选中工具的 readonly 分身中使用；不授予通用 message、exec 或 admin。这是对当前安全/工具契约的一项明确扩展，需维护者确认，不能以插件的全局权限绕过。

主会话仍经事件与绑定接收，结合原发送者及既有授权决定代查、执行、拒绝或请主人确认。群成员发言不能自动变成主人的高权限指令。结果通过现有异步等待/完成通知回到原群分身，由它选择是否公开及回复哪条消息。主会话不能递归请求自己；相互等待和取消沿现有后台调用链处理，不增加轮询判断模型或另一套审批系统。

### 群分身的行为约束

只需要短而具体的指令：了解本轮有哪些未读消息；可以安静；有明确帮助再参与；回复具体消息而不是逐条点评整批；区分机器人自己的发言；读记忆用于理解，不泄露私人内容；需操作时向主会话请求；拿到真实结果再报告完成。实际措辞按 yonder-prompt-design 装配审核，不另造人格系统。

## 4. 改动位置与实施顺序

| 步骤 | 最小改动 | 交付条件 |
|---|---|---|
| A 接收旁观 | QQ SDK 事件映射、mention passthrough、现有 write 语义 | 真实非 @ 入站与 @ 读取前文；普通消息无模型调用 |
| B 群持续参与 | QQ 插件窗口与游标、绑定/配置命令；通用 message_send.replyTo 与投递校验 | 一批多消息一次初始运行，模型自主沉默/定向发送，跨群隔离 |
| C 只读分身与主会话请求 | 选择 read 工具/上下文；审核后的受限内部请求工具与绑定 | 读共享记忆，写/exec 被拒绝；请求到 main，真实结果回来再交付 |
| D 连续真实验证 | 隔离 home，现有 Luna 和同一测试 QQ | 忙时新消息、空闲无调用、重启恢复、真实送达与用量证据 |

先修现有共享缺口，再补 QQ 接线；不新增通用群聊框架、独立判断服务或数据库。首版扫码接入与后续群参与各自记录验收，不把 A 当成 B/C 完成。

## 5. 验收清单

1. 私聊、群 @ 保持原先真实收发闭环。普通文字消息取得 QQ 原生 ID，经 mentioned=false 写入该群会话，未产生 run；@ 后模型能引用此前真实内容。
2. 两个群各有独立 persistent 会话，单群多人身份保留；私聊 main 不混入群上下文。
3. 同一窗口的多条真实消息只生成一次初始运行。闲置窗口零调用；模型可以一条也不发，或指定其中某条回复，QQ 客户端核实实际目标。
4. 同群运行期间的新消息仍在下轮未读范围；重启后已接纳输入不重复运行，发送未知不自动补发。
5. 群分身能读已有共享 memory 文件，写和 exec 被拒绝；未获得会话历史管理能力。向 main 的请求带真实群来源，返回真实结果后才声称完成。
6. 记录 run 数、模型请求数、输入/输出 token、公开发言数、处理延迟及投递结果。实测后再调整窗口或评估判断模型。

测试始终使用独立 home；不重启、不替换用户日用安装。B/C 尚需上述契约审核与实现，不能用当前 A 的协议测试或先前私聊/群 @ 验收代替。
