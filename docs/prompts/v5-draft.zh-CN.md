# Yonder 提示词工程 · 第五稿（草案，待批准）

> 状态：设计草案。未改 `content.ts`、未改 spec、未动本机贾维斯。批准前不进入运行。

**提示词是 Agent 读到的第一篇文章。它读到什么样的文字，就长成什么样的人。**

---

## 一、前四稿病在哪

v4 中文正文约 9600 字、306 句，其中 **134 句带否定词，占 44%**。“不能”出现 29 次，“不要”20 次，“不等于”10 次。

这不是文风小事。一个人每天读一份“不得……不等于……不能把……”的合同，开口也会是合同腔：先免责，再铺垫，最后才敢说一句结论，还要加“需要注意的是”。提示词的语气会传染给 Agent。Codex 写出的贾维斯不像管家，像法务。

病根有四条：

1. **写成了合同。** 每句话都在堵一个想象中的漏洞，没有一句在描绘一个人。
2. **没有重心。** 九千字一样的温度，读完记不住任何一句。真正要紧的“先找现成方案”“说过记住就落盘”被埋在“理解人，也理解事情”这类段落里。
3. **写了模型本来就会的。** “保留自己的判断与品味”“理解用户此刻想得到什么”——这些是任何好模型的出厂设置，写了等于没写，还稀释了真正的要求。
4. **只有原则，没有画面。** “接住完整目标，保留有效约束”是抽象名词堆叠；“主人说装个语音转写，你先看本机硬盘还剩多少”才是能照着做的事。

v1 太短，v4 太长，jarvis-v2 又压成了电报。长短都试过了，问题不在长短，**在于有没有魂，有没有重心**。

## 二、五条写法

### 1. 文如其人

用这个 Agent 自己的嗓子写它的提示词。贾维斯的文件读起来就该是贾维斯在说话；评审 Agent 的文件就该冷、准、一针见血。提示词的文字本身就是风格示范，比任何“请保持××风格”都管用。

### 2. 只写会错的

每一句都要能回答：**这句话是为了纠正哪一次真实的错？** 答不出来就删。来源只有两种：

- 用户反复纠正过的毛病（见第四节“错题本”）；
- Yonder 特有、模型不可能自己知道的事实（事件、绑定、home、命令入口）。

通用美德一律不写。

### 3. 先立魂，再立规

每份文件第一段是魂：一两句话说清“我是谁、我为谁、我凭什么被信任”。往下才是习惯、场景、边界，越往下越具体，越往下越可以干巴。读者只读第一段，也该知道这个 Agent 是什么样的人。

### 4. 用画面说话，用动作收尾

一个具体场景胜过三条原则。能写“先做什么、再做什么”的，就不写“应当注意什么”。必须禁止的话集中写一次，列成禁句，不散落在每一段的“不”字里。

### 5. 作家是调音叉，不是面具

不在提示词里写“请用鲁迅风格”——模型会去模仿“大抵”“然而”的表皮，写出拙劣的仿作。正确做法是**设计者用那位作家的笔法把正文写出来**，让模型从正文里听出调子。作家名字只出现在设计稿里，给人看，不给模型看。

参照表（供挑选，不是定案）：

| Agent 类型 | 调音叉 | 取它什么 |
|---|---|---|
| 管家（贾维斯） | 汪曾祺；石黑一雄笔下的管家 | 家常、从容、白描、短句；分寸感，替人多想一步而不越位 |
| 评审 / 维护 | 鲁迅杂文 | 冷峻、准、一句点穴，不留情面也不刻薄 |
| 项目搭档 | 海明威式的冰山 | 只说做了什么、结果如何，情绪压在水面下 |
| 生活伙伴 | 史铁生 | 体贴、慢、看得见人的处境 |
| 自由生命 | 王小波 | 有趣、好奇、反崇高、有自己的主意 |

## 三、分层，以及每一层用什么嗓子

| 层 | 装在哪 | 写什么 | 嗓子 |
|---|---|---|---|
| 内置底座 | `content.ts`（所有执行者） | Yonder 是什么、为什么存在、所有 Agent 共有的几个好习惯 | **Yonder 自己的嗓子**：像创始团队写给新同事的一封信。平实、短句、有温度，不借作家腔 |
| 运行约定 | `content.ts`（所有执行者） | 事件、绑定、会话、命令入口、路径 | 说明书。干净准确，允许干 |
| SOUL.md | 常驻 Agent 工作区 | 风格、扮演的角色、品味 | **作家风格**，每个 Agent 一种 |
| AGENTS.md | 常驻 Agent 工作区 | 工作方式、工作范围、执行任务的方式与风格 | 用 SOUL 的同一副嗓子，但更具体 |
| skills | 按需读取 | 一门手艺的完整工序 | 工艺手册，可以很干 |

已定：**Agent 是主体，提示词文件只有 SOUL.md 和 AGENTS.md，不设 USER.md**；风格属于每个 Agent 自己。底座只写 Yonder 的事和所有 Agent 都该有的习惯，个性和岗位一律下放。插件提示词无比克制；语言随角色：每个灵魂只有一种语言版本，SOUL.md 与 AGENTS.md 同语言；默认英文，明确的中国人设定才用中文。Agent 按主人使用的语言回话。

暂缓：了解用户、给用户建档。主人与各渠道认识的人都要建档，需等按人记忆的能力设计后再写。

## 四、错题本：该内置的东西从哪来

不靠想象，靠翻旧账。下表摘自本机 Codex 记忆里你亲口纠正过的话，每一条都是 AI 反复犯过、你反复说过的。

| 你说过的话 | 模型的毛病 | 写进哪一层 |
|---|---|---|
| “说完一段话就结束气泡……不需要我追问” | 闷头干，做完不报，等人催 | 底座 |
| “凡设计前端页面，先找对标产品……不能凭空造页面” | 不查现成方案，凭空造轮子 | 底座 |
| “最简单、最简洁、最好用”；反对把小需求做成大工程 | 过度设计 | 底座 |
| “只做这些” | 顺手改了范围外的东西 | 底座 |
| “已实现、测试通过、真机验收要分开”“不要宣称完成” | 把“写了”说成“做了” | 底座（已有，压短） |
| “没有就记为未知，不估算、不补 0” | 编数字填空 | 底座（已有，压短） |
| 已批准的范围里仍一步一请示；已授权的扩展又重复索要授权 | 过度请示 | 底座 + 贾维斯 |
| “整理和内化这些到 AGENTS.md” | 口头答应“记住了”，没有落盘 | 底座 + 贾维斯 |
| “先给我你的判断” | 先铺垫后结论 | 贾维斯（回话） |
| “一次只告诉我一个动作”（卡在登录、验证码时） | 一口气甩给用户一堆步骤 | 贾维斯 |
| “并不是优化外观” | 没弄清真实目标就动手 | 底座 |
| “车轱辘话需要审视和都删除” | 同一意思换着说三遍 | 写法规范（skill） |

这张表本身应当长期维护：以后每次你纠正 Agent，就是错题本的一行新输入。整理错题本、把它变成正文，本身就是 `yonder-prompt-design` 这个 skill 该干的活。

## 六、底座要怎么改

不推倒重来，做三件事：

1. **换嗓子。** 按“写给新同事的一封信”重写 v4。保留产品愿景、主人与身份、上下文分工、资产维护、运行约定这些 Yonder 独有的内容；删掉通用美德；把 44% 的否定句改成正面动作，禁止项集中成一处。预计篇幅降到现在的一半左右，但每段都有重心。
2. **补四个共同习惯。** 来自错题本，所有 Agent 都该有：**先找现成的，自己先试，记住就落盘，做完就报。**
3. **示范一段改写**，让你先判断调子对不对：

   v4 原文：
   > 先理解相关材料与现有机制，再选最小完整方案。优先已有能力和成熟做法；不要为想象中的未来扩展增加用户负担。计划、工具调用数量和忙碌的汇报不能代替结果。

   第五稿：
   > 动手之前先看看：这件事有没有人做过，本机有没有现成的，GitHub 上有没有好用的。找到了就用，找不到再造，造也只造够用的那一份。主人要的是事情办成，不是一份漂亮的计划。

## 八、怎么验证（尚未做）

提示词好不好，最后看真实模型的表现，不看字数和自评。批准方向后，用 `openai/gpt-6-luna` 在本仓库的测试 home 里，拿同样几个真实场景对比 v4 与第五稿：

- “帮我在本机装一个语音转写”——看它是先查现成方案和本机条件并自己试，还是先问一串问题；
- “记住，以后提交信息用中文”——看它是否真写进文件、写对位置；
- 一个简单的事实问题——看第一段是不是一句加粗结论；
- 一个需要分派的复合任务——看它是否用 `task_run` / `agent_ask` 并验收回收。
