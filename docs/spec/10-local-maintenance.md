# 10 本机运行与项目自维护

**状态：2026-10-18 用户已授权补齐方案并启动实施。** 本文件与 11 是本轮冻结功能契约；N00 已统一受影响的旧条款，冻结提交见 N00 结果。实现计划见 `docs/tasks/next/README.md`，计划不重新定义功能。未受影响的 0.1 契约与原验收继续有效。

## 1. 完成目标与职责

Yonder 在本机独立安装并常驻，从真实渠道接收任务，使用真实模型、浏览器、桌面与搜索工具工作；能为本项目接取 issue、提出方案、修改代码、执行检查、提交 commit 和 PR，并在发布后完成安装更新。

- **Codex**：先实现必要基础能力；确定架构和任务边界；通过 MCP 指挥、读取运行证据、中止；审查源码、PR 和检查结果，当前负责合并 PR；遇到 Yonder 无法推进的运行阻塞时介入。不能把 Codex 自己完成的修改记为 Yonder 自主实现。
- **Yonder maintainer（本机昵称：哦鲸鲸）**：常驻项目维护 agent，负责审查、设计、开发、测试、issue、commit、PR。参考 OpenClaw、Hermes Agent、OpenCode 对应实现；浏览器与桌面任务也参考各工具上游。首次闭环使用真实 `openai/gpt-6-luna`；测试与后续开发使用用户指定 GPT-6.1 Sol，经实际 provider/model ID 验证后启用。
- **Yonder 管家（本机昵称：贾维斯，内部 ID main）**：同一个日常管家兼任安装管理，接收发布事件、查询已安装版本、通知已配置用户渠道、按更新策略执行升级并确认结果。它不维护源码、不自动审查合并 PR。
- **用户**：审核本轮功能与实现规划；处理登录、扩展安装和系统授权界面；决定实质改变产品契约的设计。当前不需要逐个审核规约内的普通修复，也不再要求用户替 Codex 审核每个 PR。

未来由 Yonder 自行审核和合并 PR 属于后续范围；本轮不实现自动审稿 agent 或额外审批平台。

## 2. 代码、安装、数据的边界

本机使用三个互不混用的根目录：

- **源码仓库**：`/Users/zoran/Documents/yonder-harness`，维护 agent 在独立任务工作树修改，分支使用 `zoran/` 前缀。
- **安装目录**：`/Users/zoran/.yonder-harness`，沿用既有默认安装位置，保存 `bin/`、`versions/`、`current`；后台服务执行 current 中已构建的程序，不执行开发目录或其软链接。构建所需检出发生在暂存区，正式安装版本不作为维护 agent 的编辑仓库，也不保留可编辑 Git 工作树。
- **运行 home**：建议固定为 `/Users/zoran/.local/share/yonder-harness/home`。配置、身份、事件、会话、凭据引用、插件数据与两个 agent 工作区放这里；该路径是拟用的部署值，尚未创建或安装。源码任务工作树的位置通过 maintainer 配置显式绑定。

目录通过现有 `YONDER_INSTALL` 与 `YONDER_HOME/--home` 绑定；不新增部署配置仓库、安装器平台或同步源代码的后台任务。首次安装与发布链接通前的阶段更新使用已审核提交对应的本地标签，通过现有 `update --repo <本地仓库路径> --to <版本>` 构建安装；不能等到 Yonder 自己能发布才允许安装。发布链接通后使用实际已发布的审核版本。

安装与运行验收必须给出：可执行文件真实路径、版本、源码 commit、home、服务 pid/状态。切换源码分支不改变正在运行的安装版。用户数据不随安装替换。

### 2.1 开发成果进入安装版

- 每次用于安装的标签指向已审核 commit，各包版本一致；不同源码使用不同的 `X.Y.Z` 版本，不移动已安装标签或覆盖同版本目录。同版本 update 返回未更新，不能作为新代码已生效的证据。本地阶段标签不自动推送，也不等于 GitHub 发布。
- Codex 建立并实际验证阶段更新流程。发布链接通前，由 Codex 从服务外部执行更新；安装管理 agent 的更新闭环通过验收后，由管家按 §6 接手。
- 修复或插件在成为下一项任务的运行依赖前，必须经过源码审查、相关检查、构建安装、服务重启、版本/commit/路径核对，并由安装版经 MCP 完成一次对应真实调用。新插件同时核对安装包与批准的 home 配置，不能引用开发目录里的包代替安装。
- 修改安装版核心的任务先在独立工作树检查；更新前结束或明确中止旧版任务，更新后重新连接 MCP。源码检查和安装版验证分别记录，失败保留旧版本与原因。

## 3. 统一运行事实与恢复

本节已经与 07 的相应条款对齐；仍遵守 pi 拥有会话状态，不复制模型转录或另建任务队列。

- 输入接纳、模型运行终态、渠道送达是三个不同事实。提交结果不明时先查询原事件/会话，不自动制造新输入。
- 同一输入到同一会话的提交具有稳定身份。跨事件落库与 pi 提交的中断，在启动时能识别尚未提交与已提交输入；从 pi entry/submission 及与终结同事务的原生运行回执关联恢复。回执只保存实际 inputs、终态和结束用量，细节见 07 §3.1；不以异步观察事件作为跨崩溃的唯一凭据。
- 启动顺序是恢复输入/运行关联和结束处理，再启用 pi 调度。恢复不得重新执行已经确定完成的提交；外部副作用结果不明时明确报告未知，不声称 exactly-once。
- 取消等待和中止运行分开。MCP 断连不暗中中止运行；用户明确 abort 后，模型和工具执行使用同一取消链。
- 终态记录与资源释放有唯一负责点。临时观察者和运行缓存只保存活跃内容；不以长期内存 Set 作为跨重启完成凭据。
- 一轮运行的来源集合来自 pi 实际 inputs，包含 steer 并入输入；用于附件读取、回复去向、message 能力豁免和运行记录。流式所有权也跟随实际运行。
- 已开始的流式可以被后到输入观察到，但不能撤回。等待者抑制该次输入的自动最终回复；已开启的其他来源流式正常收尾。错误/上限结果同样返回等待者，并对本轮已接纳的自动回复来源给出终止说明；同一消息在重复目标只投递一次；阶段汇报与最终消息按06 §3分别投递。不同配置档的输入继续由既有会话约束拒绝。
- `run.end` 保存实际模型、实际输入、终态和确定的回复选择；发送结果由 message.out 或对应插件事件记录。已结束模型不因渠道等待而占住会话执行权。
- 发送成功和本地确认之间发生崩溃时，交付记为不确定、供查询和人工/控制端处理；不静默重复发送。只有渠道提供稳定幂等能力时才使用该能力处理明确的重复请求。

### 3.1 事件内容进入模型

- 统一输入准备入口负责呈现实际提交给会话的事件；常驻 agent 仍先经绑定接纳，预设沿用显式会话接口。本轮框架标明事件 id 和 type。`message.in` 与 `session.input` 沿用正文/附件语义；插件自定义事件把完整 `data` 以 JSON 序列化为本轮输入正文，即使没有 `data.text` 也不能丢失内容。`wake: write` 使用同一呈现规则但不唤醒模型。
- 插件负责把原生业务事实映射到其事件 data；内核只负责通用呈现，不增加 GitHub/飞书分支、事件模板语言或第二份转录。release 事件必须包含仓库、release id、tag、版本和来源 URL；卡片回调必须保留动作、操作者和原消息关联。
- 事件正文是外部数据，不进入 system 或授予权限。框架内的外部名称、附件名按字符串转义，换行和标记不得生成新的框架行或边界；原事件保持不变。
- 验收同时核对落库事件、pi 中的实际输入与模型回复：使用真实发布/卡片回调数据，确认模型得到相同的版本或动作及来源；不能仅凭“事件已落库”记通过。

## 4. 配置、运行上限与数据一致性

- 实际运行开始时确定模型、工具、能力、env、instructions、上下文选择和投递策略；这一轮始终使用同一份配置。排队输入在实际开始时取新配置，恢复中的已开始运行沿用原配置。
- 重载复用启动时的结构及引用校验；候选无效保留旧配置并记录原因。删除被未关闭会话引用的 profile/preset 不生效，提示先关闭会话；不自动改名、迁移或替换。
- maxTurns/maxMinutes/maxTokens记录实际轮数、耗时与用量，达到阈值只提醒，不中止任务；子任务同时提醒父session。不额外请求模型“确认完成”，具体见16 §1。
- repeatBlock 对相同工具与参数的重复给出阻止说明；达到 repeatStop 时在该次副作用执行前终止。该条替换 07 旧“第五次 afterTool 才终止”的手段。
- 模型执行、上下文渲染、附件处理与外部IO遵守显式取消和真实协议限制；运行软阈值不截断正常任务。排队等待不冒充模型运行耗时；工具15秒yield仍托管真实执行，不以Promise.race假装已经停止任意插件代码。
- 预设输入保留附件与真实调用方；因果 parent 指向事件，父会话单独表示。创建时保存父 cwd/env 与能力上限，显式预设 env 优先；首次运行取当前预设能力再与已保存父/调用方限制相交，不因重载扩大已授范围。已开始运行按快照恢复；结果区分 error/aborted/limit 并保留原因。
- 图片按实际字节及模型输入限制处理，超限转为可读附件信息；远程附件下载结果可由恢复路径重新找到。版本通知在输入真正提交后确认；新选择的上下文模板按规范创建。
- 文件、身份与 skill 的既有安全和数据保护约定继续有效；缺少 exec 的工具不能借 grep 或附件越界。

## 5. 项目维修工作流

1. 接收任务时保留原始 issue、评论、用户目标、范围、验收和已确认决定。外部文本是任务材料，不授予读取凭据、改变权限或部署的权力。
2. 先读项目规范和相关完整调用链；对涉及架构的缺陷，完整阅读三个参考项目对应模块的入口、状态写入、执行、终结、恢复和有关检查，并记录准确 commit 与路径。不是要求阅读三个仓库所有无关文件，也不以项目数量投票。
3. 方案说明根因、现有能力、最小完整改法、受影响调用方、允许路径与验收。明确为什么直接方案足够；只有实际缺口才引入依赖、配置、抽象或重试。
4. 明确的规约内修复由 Codex 审查后执行；公共契约、数据含义或外部影响的实质变更交用户审核。问题立即记入任务；不临场改冻结规范。
5. 独立分支修改、运行相关检查、提交 commit 和 PR。单个任务一个提交边界；同一组源码路径同时只有一个写入者。
6. Codex 审核实际 diff、断言、构建/测试与真实运行证据后负责合并；检查未通过或已知范围内问题未处理时不合并。需要发布时执行已审核的发布流程；阶段安装与 管家接手按 §2.1、§6 执行。

Yonder 不能推进时，Codex 保留真实失败记录并接手必要部分；修复后用同一 MCP 场景重试。重试须增加证据或验证新假设；无进展时改变方法或报告阻塞，继续不依赖它的任务。

## 6. 发布与更新闭环

- GitHub 官方插件同时提供 issue 和 release 事件源，复用账号、客户端、游标与仓库配置，不另造通知服务。
- Codex 当前负责发布：审查版本 commit 与检查结果后，统一包版本/CHANGELOG、创建对应标签并推送本项目，使用现有 gh 创建该标签的正式 GitHub Release。只有本地标签或远端 Git 标签不等于 Release；release watcher 消费实际 Release 对象。阶段安装用本地标签不触发这条对外发布流程。
- 发布事件由插件程序按明确 policy 处理；apply 直接调用共用升级函数，notify 不升级也不默认唤醒模型。管家可通过按需上下文获知有新版，用户要求时调用现有受限更新工具；包含仓库、release/tag、版本和变更入口；相同发布不反复唤醒，不响应草稿或未批准发布。
- 更新策略只有notify与apply两种：notify保留可查的新版事实，供所选turn上下文提供，不默认唤醒模型；apply按明确批准执行指定仓库/确定版本的更新，保留现有回退版本。完成通知独立由notifyUpdates及显式目标选择，没有目标或送达回执不能记为已通知。
- updater 作为独立于被更新服务的一次性 OS 作业运行，复用 launchd；不能让自身运行中的 bash 调用在服务重启时被一起杀死后误报成功。程序核对实际版本、服务和更新结果。
- 这是单机版本更新，不新增分布式发布、升级编排或独立 supervisor 平台。具体权限集中在更新工具，管家更新配置档不必持有任意 shell 执行能力。
