# 10 运行保证与发布更新

运行事实、恢复、配置快照与发布更新的跨层契约，与 07（pi 对接）、09（CLI 与发布）配合阅读。

## 1. 统一运行事实与恢复

本节与 07 对齐；pi 拥有会话状态，不复制模型转录或另建任务队列。

- 输入接纳、模型运行终态、渠道送达是三个不同事实。提交结果不明时先查询原事件/会话，不自动制造新输入。
- 同一输入到同一会话的提交具有稳定身份。跨事件落库与 pi 提交的中断，在启动时能识别尚未提交与已提交输入；从 pi entry/submission 及与终结同事务的原生运行回执关联恢复。回执只保存实际 inputs、终态和结束用量，细节见 07 §3.1；不以异步观察事件作为跨崩溃的唯一凭据。
- 启动顺序是恢复输入/运行关联和结束处理，再启用 pi 调度。恢复不得重新执行已经确定完成的提交；外部副作用结果不明时明确报告未知，不声称 exactly-once。
- 取消等待和中止运行分开。MCP 断连不暗中中止运行；用户明确 abort 后，模型和工具执行使用同一取消链。
- 终态记录与资源释放有唯一负责点。临时观察者和运行缓存只保存活跃内容；不以长期内存 Set 作为跨重启完成凭据。
- 一轮运行的来源集合来自 pi 实际 inputs，包含 steer 并入输入；用于附件读取、回复去向、message 能力豁免和运行记录。流式所有权也跟随实际运行。
- 已开始的流式可以被后到输入观察到，但不能撤回。等待者抑制该次输入的自动最终回复；已开启的其他来源流式正常收尾。错误/上限结果同样返回等待者，并对本轮已接纳的自动回复来源给出终止说明；同一消息在重复目标只投递一次；阶段汇报与最终消息按06 §3分别投递。不同配置档的输入继续由既有会话约束拒绝。
- `run.end` 保存实际模型、实际输入、终态和确定的回复选择；发送结果由 message.out 或对应插件事件记录。已结束模型不因渠道等待而占住会话执行权。
- 发送成功和本地确认之间发生崩溃时，交付记为不确定、供查询和人工/控制端处理；不静默重复发送。只有渠道提供稳定幂等能力时才使用该能力处理明确的重复请求。

### 1.1 事件内容进入模型

- 统一输入准备入口负责呈现实际提交给会话的事件；常驻 agent 仍先经绑定接纳，预设沿用显式会话接口。本轮框架标明事件 id 和 type。`message.in` 与 `session.input` 沿用正文/附件语义；插件自定义事件把完整 `data` 以 JSON 序列化为本轮输入正文，即使没有 `data.text` 也不能丢失内容。`wake: write` 使用同一呈现规则但不唤醒模型。
- 插件负责把原生业务事实映射到其事件 data；内核只负责通用呈现，不增加 GitHub/飞书分支、事件模板语言或第二份转录。release 事件必须包含仓库、release id、tag、版本和来源 URL；卡片回调必须保留动作、操作者和原消息关联。
- 事件正文是外部数据，不进入 system 或授予权限。框架内的外部名称、附件名按字符串转义，换行和标记不得生成新的框架行或边界；原事件保持不变。
- 验收同时核对落库事件、pi 中的实际输入与模型回复：使用真实发布/卡片回调数据，确认模型得到相同的版本或动作及来源；不能仅凭“事件已落库”记通过。

## 2. 配置、运行上限与数据一致性

- 实际运行开始时确定模型、工具、能力、env、instructions、上下文选择和投递策略；这一轮始终使用同一份配置。排队输入在实际开始时取新配置，恢复中的已开始运行沿用原配置。
- 重载复用启动时的结构及引用校验；候选无效保留旧配置并记录原因。删除被未关闭会话引用的 profile/preset 不生效，提示先关闭会话；不自动改名、迁移或替换。
- maxTurns/maxMinutes/maxTokens记录实际轮数、耗时与用量，达到阈值只提醒，不中止任务；子任务同时提醒父session。不额外请求模型“确认完成”，具体见14 §1。
- repeatBlock 对相同工具与参数的重复给出阻止说明；达到 repeatStop 时在该次副作用执行前终止。
- 模型执行、上下文渲染、附件处理与外部IO遵守显式取消和真实协议限制；运行软阈值不截断正常任务。排队等待不冒充模型运行耗时；工具15秒yield仍托管真实执行，不以Promise.race假装已经停止任意插件代码。
- 预设输入保留附件与真实调用方；因果 parent 指向事件，父会话单独表示。创建时保存父 cwd/env 与能力上限，显式预设 env 优先；首次运行取当前预设能力再与已保存父/调用方限制相交，不因重载扩大已授范围。已开始运行按快照恢复；结果区分 error/aborted/limit 并保留原因。
- 图片按实际字节及模型输入限制处理，超限转为可读附件信息；远程附件下载结果可由恢复路径重新找到。版本通知在输入真正提交后确认；新选择的上下文模板按规范创建。
- 文件、身份与 skill 的既有安全和数据保护约定继续有效；缺少 exec 的工具不能借 grep 或附件越界。

## 3. 发布与更新闭环

- GitHub 官方插件同时提供 issue 和 release 事件源，复用账号、客户端、游标与仓库配置，不另造通知服务。
- 发布流程：统一包版本与 CHANGELOG，创建标签并用 gh 创建该标签的正式 GitHub Release。只有本地标签或远端 Git 标签不等于 Release；release watcher 消费实际 Release 对象。阶段安装用本地标签，不触发这条对外发布流程。
- 发布事件由插件程序按明确 policy 处理；apply 直接调用共用升级函数，notify 不升级也不默认唤醒模型。常驻 Agent 可通过按需上下文获知有新版，用户要求时调用现有受限更新工具；包含仓库、release/tag、版本和变更入口；相同发布不反复唤醒，不响应草稿或未批准发布。
- 更新策略只有notify与apply两种：notify保留可查的新版事实，供所选turn上下文提供，不默认唤醒模型；apply按明确批准执行指定仓库/确定版本的更新，保留现有回退版本。完成通知独立由notifyUpdates及显式目标选择，没有目标或送达回执不能记为已通知。
- updater 作为独立于被更新服务的一次性 OS 作业运行，复用 launchd；不能让自身运行中的 bash 调用在服务重启时被一起杀死后误报成功。程序核对实际版本、服务和更新结果。
- 这是单机版本更新，不新增分布式发布、升级编排或独立 supervisor 平台。具体权限集中在更新工具，更新用的配置档不必持有任意 shell 执行能力。

### 3.1 程序更新与通知

版本检查、确定性升级/核验/通知不要求模型中转；完成事实统一为release.update-result。程序通知仅显式开启时发指定目标；Agent仅按明确run/write订阅获得事件，无订阅不调用模型。
