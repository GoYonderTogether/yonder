## 执行顺序与交付

1. **N00–N03｜基础与安装。** Codex 对齐冻结规范、落实事件呈现与运行边界、接通 MCP 和独立安装。N00 启动桌面/hosted search/Sol 的最小试通，N03 验证 Yonder 内的模型；阻塞记回对应任务。
2. **N04–N05 → N09｜自主修复与核心验收。** Yonder 完成小修复；Codex 先确定共同根因的技术方案，再由 Yonder 修复恢复/投递；Sol 补测试与旧缺陷。核心验收不等待桌面、搜索或浏览器。
3. **N10 → N11｜GitHub 与发布更新。** 在核心验收具备后，由 Yonder 实现 issue→PR 和发布→operator 更新，Codex 审查合并及发布。
4. **N06、N07、N08｜独立工具任务。** N03 后即可分别推进；共享源码路径顺序写入，登录或权限阻塞只影响相应能力。Computer Use 与 hosted search 分别记录结果，不互相冒充通过。
5. **N12 → N13｜飞书。** N09 后可开发飞书，不依赖 GitHub 自动更新；真实客户端验收另依赖 N06 的桌面能力与已安装飞书包。
6. **N14｜整条链收尾。** 各能力分别通过后，从安装版验证完整维护与日用链，完成原验收剩余项。

以上是建议顺序；硬依赖只看任务清单。允许在等待外部授权时执行满足依赖的任务，全部目标继续保留。

## 实现方式

- 官方插件采用主仓库独立 workspace 包，接口只经 SDK；同一次任务允许修改自身包、必要构建清单、该任务检查与记录。
- N02 之前由 Codex 建基础；N03 以后大多数源码工作交给真实 Yonder。Codex 子 agent 的工作不算 Yonder 自主实现。
- 同一源码路径只有一个写入者。无冲突的纯阅读和检查可并行；不为并行增加调度平台。
- 按任务提交，实际验证写回对应结果；Codex 当前负责 PR 审查与合并。普通实现选择沿用已批授权，实质改变功能再提交精确文档变更。
- 已安装版本、运行 home 和开发源码分开。N03 建立阶段安装流程；N04–N13 的成果在成为运行依赖前，由 Codex 按 10 §2.1 执行安装与真实调用，N11 更新闭环通过后交 operator。记录在产生成果的任务内，不能以源码检查替代安装证据。
- 使用最新参考材料前更新仓库，再固定实际 commit；上游变化不自动修改已经冻结的功能。
