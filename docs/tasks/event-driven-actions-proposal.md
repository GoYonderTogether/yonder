# 事件驱动程序动作：最小方案

日期：2026-10-19。状态：用户已批准 E0–E4，正在实施；本机更新配置尚未切换。用户要求通用事件可选择模型、程序、脚本或插件处理；不能只针对版本升级省一次调用。

## 1. 判断

当前更新链把“读取明确发布→按已批准策略升级→按真实回执通知”固定步骤交给模型做工具选择。步骤无需模型判断时，两次模型运行可以移除。模型只承担需要理解任务、选择行为或解释异常的部分，不充当每次自动化的中转。

无需建立工作流引擎。现有事件账本、绑定、插件 events.on、messages.send、原生 write 输入以及既有更新作业是基础；先补真实缺口，不能把接口存在等同更新链已经如此运行。

## 2. 当前源码事实

| 能力 | 当前状态与边界 |
|---|---|
| 插件订阅事件 | 已有 api.events.on(type, handler)，精确类型或prefix.*；handler收到完整YEvent。setup注册，同插件串行，不等待模型终态；不能拦截或改写原事件 |
| 不唤醒模型保存背景 | Agent绑定已有wake:write，走原生pi输入，不运行模型；没有绑定的事件仅记录，不自动成为某Agent的上下文 |
| 无模型发送渠道消息 | 已有api.messages.send，显式person/acct/conv目标；消息归属plugin身份，发送结果记录message.out，不冒充Agent回复 |
| 插件/程序观察历史 | 已有events.query及CLI events分页；实时events.on仅限进程内插件，不是现成的外部脚本订阅CLI或持久消费队列 |
| 程序更新 | GitHub插件已有独立launchd更新函数和真实result.json；目前仍由模型工具触发和模型发送通知 |
| 已安装版本提示 | 已有turn.notice，当前版本与会话记录版本不同时在下一次实际输入提示已经更新；不额外唤醒模型 |

## 3. 通用处理方式

事件先记录原始事实，然后各消费者按已有配置处理。程序订阅与Agent绑定是两条独立路径；可只选一个，也可明确同时选择，不新增“默认先问AI”的步骤。

| 消费方 | 用途 | 是否调用模型 |
|---|---|---|
| 无消费者 | 留下事件事实，供日后查询 | 否 |
| Agent，wake:write | 收入会话背景，下次正常对话再看 | 否 |
| Agent，wake:run | 理解内容、决策或完成复杂任务 | 是 |
| 插件events.on处理器 | 根据原数据执行已定义动作、生成产物或发通知 | 否 |
| 插件连接的脚本/程序 | 对固定且已授权的程序传事件数据，读取实际退出码/结果 | 否，除非程序本身调用模型 |

程序动作复用实际业务函数。例如update_schedule工具与事件回调共享scheduleUpdate，不构造假的ToolContext，不通过虚构Agent或模型工具调用来执行代码。模型工具入口继续校验模型运行能力；程序入口按显式插件配置和授权判定，不能把外部事件当成exec/admin授权。

脚本只是可由可信插件接入的一种消费者：固定已授权的可执行文件/脚本，JSON经stdin或结构化参数传入；不把事件正文拼进shell命令。源码插件可直接注册handler；不为尚无明确使用者的任意脚本管理器新增安装、配置、重试和调度系统。

## 4. 更新作为首个真实场景

1. GitHub插件沿用当前轮询、批准仓库/作者、正式发布校验与接收基线，保存可升级版本事实。
2. notify策略：没有自动升级，也不唤醒AI。所选上下文贡献在下次正常对话的turn中提供已核实的可升级信息；保持system稳定，不在每次聊天重新联网查询。不把Release正文当作指令，不自动加载为新任务。
3. 用户说“帮我升级”：当前对话模型理解并调用一次已有调度工具；实际构建、安装、重启及核验仍由程序执行，不额外创建版本管理Agent或后续核验模型运行。
4. 用户直接运行yonder update：CLI执行升级，不调用模型。当前CLI升级与GitHub的独立作业并非同一个完成事件源；本轮必须补共同完成事实，否则不能声称CLI升级也能触发相同订阅通知。
5. apply策略：仅已明确批准的配置允许，插件直接调用共享升级函数，无需先唤醒AI来决定是否执行。用户本机此前批准的apply策略仍保留，未因本方案悄悄改变。
6. 升级成功或失败产生可核对的完成事件；没有订阅者就只记录，不默认唤醒贾维斯。选择程序通知订阅时，根据真实核验字段生成简短消息并直接用messages.send发往明确目标；只有明确订阅了模型处理时才唤醒模型。
7. 贾维斯如需了解结果，使用write背景或下次输入的已更新notice，而不是为了“知道已经更新”单独调用模型。失败是否交给Agent分析也由订阅策略明确指定，不能每次失败默认扩展权限或无限重试。

机器核验继续负责真实version/commit/home/pid/ready；没有充分证据时程序写“失败/未确认”，不让模型猜成功。现有外部结果未知不自动重发的规则保持。

## 5. 通知目标必须分开

- **外部会话conv**：飞书群/私聊或真实渠道，用现有messages.send，无需模型。
- **Agent会话背景**：经已有事件绑定与wake:write，记录原始来源，不自动回答。
- **指定内部session的程序通知**：如用户需要直接看到在某段TUI任务历史中，应增加一个窄的非模型通知契约：真实程序来源、目标session、原始event引用、正文、记录/展示回执；不伪造assistant/user发言，不调用sessions.submit来假装通知，也不复制pi转录到另一张表。

最后一项尚需核实原生pi允许的带来源的注记/展示入口，先确定存储与观察语义再冻结API名称。常驻Agent的工作输入仍走绑定；通知不能成为绕过绑定或会话权限的隐藏任务入口。若仅需外部渠道通知和write背景，则无需为首个更新链引入该接口。

## 6. 必须保留的实际执行语义

- events.on当前是进程内观察，不是持久任务队列；崩溃前落库、回调未执行的事件可能只有账本事实。不能对任意脚本承诺必执行或exactly-once。
- 更新继续复用其已有接收基线、原生release ID和每次更新回执，避免重复安装；通知复用已有发送结果/未知语义，不对未知结果盲目重发。
- 订阅者自己的恢复需求用现有query和具体业务状态处理；不为了未来通用场景新增全局outbox、消费数据库、自动重试平台或脚本沙箱。
- 原始事件不变。处理结果用新的插件自定义事件表达来源和因果parent；不伪造run.end或工具转录。已有更新回执的事件来源不一致问题先在功能规范中统一，不临场发明协议。
- 新增消费者不能顺便改原Agent绑定；若程序与Agent同时订阅，明确两者各自的动作，避免对同一升级/通知执行两遍。

## 7. 已批准实施顺序

**E0 契约冻结**：主路确认CLI与插件共同更新完成事实、可升级上下文和通知/模型选择；同步spec/01、04、06、09、10、11及decisions。A0–A4的Agent管理框架仍是另一项，不混入本轮。

**E1 更新程序接线**：在plugins/channel-github/复用业务函数，把已批准apply和程序通知接到实际事件处理；删除不再需要的模型运行绑定/任务指令。插件handler只处理配置的实例/仓库/目标，不注册宽泛的全部事件处理。保留原失败与历史。

**E2 共用完成事实与可升级上下文**：主路独占packages/core/src/release/、CLI实际update调用方、SDK/内核确有必要的边界；更新程序不重写。可升级信息由插件已有contexts槽提供，只按选择加载，不把远端数据注入system。不把直接CLI update遗漏为“没有GitHub release事件就无法通知”。

**E3 聚焦验证与配置切换**：仅核对程序消费者不出现run.end/模型转录、明确Agent订阅才运行、真实成功/失败回执能够通知、通知未确认不重发、现有write路径不启动模型。一次必要的实际更新需使用真实新版本并保留证据；不为验证循环制造多个版本或重复更新。正式安装按批准后的既有update流程，不从开发目录运行替代。

**E4 指定session通知边界**：如用户确认需要任意内部session展示程序通知，补最小原生入口与实际TUI展示；与渠道通知分开验收，不用飞书送达代替内部记录成功。若原生边界不足，先提交精确缺口，不再创建新通知/会话系统绕过去。
