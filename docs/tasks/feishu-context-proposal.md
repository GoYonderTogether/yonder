# 飞书上下文修订建议（用户已批准，实施中）

## 目标与事实

用户要求：区分待处理消息和历史背景，保留真实时序与所有可见参与者，由模型结合新旧对话决定回复、合并或NO_REPLY。不是每条积压都单独回答，也不是按年龄丢弃。

现有实例与证据见feishu-recovery-result.md末节。问题分为普通迟到输入丢失发送时间的实现缺口，以及自动恢复只含未接纳用户、按发送者分组的设计缺口。

## 最小行为契约

1. 一次模型输入分清“本次待处理项”和“同会话背景”。背景不再成为新任务；原生ID对应已完成输入不能因补历史重做。接纳、模型处理、外发结果使用现有账本、pi运行回执、message.out事实，不能把客户端已读或seen当作已处理。
2. 保留发送时间与接收时间。迟到输入走同一上下文准备流程；不把几十分钟前的问候显示成现在的新请求。未知时间如实标未知，不凭年龄自动忽略重要请求。
3. 按飞书原时间排列会话背景，保留消息ID、参与者/机器人身份、引用/线程和已有回复。当前未处理区间及之前一段背景受既有上下文预算约束；过大分段并明确覆盖范围，不能声称已读取缺失部分。不每轮重载整个群历史。
4. 原始输入保留自己的身份、权限与投递目标；所有参与者的可见消息可以作为背景，不因此触发运行或取得主人权限。跨发送者不能伪造成同一个owner请求；多个待处理输入继续用pi已有inbox/steer，不建第二队列。
5. 历史中已经答过、后来被新话题替代的消息可由模型决定NO_REPLY；重要旧请求可合并或单独答。运行done、NO_REPLY、投递失败分别记录；不能把“模型跑完”等同于“语义已解决”或“用户已收到”。

## 实施工序与目录

- 先由主agent更新spec/11恢复分组条款及有关输入呈现条款、决策记录，替换旧条款后冻结。
- 飞书插件：channel.ts、history.ts、protocol.ts，统一普通/迟到/恢复输入的会话背景准备，保留时序、身份和原生ID；history已有读取能力优先复用。
- 主agent负责SDK输入契约、core/prompt呈现与现有运行/投递事实接线；只在实际需要时改相关runtime/delivery调用方，不增加通用上下文平台或会话存储。
- 针对性验证：迟到旧问候+后续已回复对话、重要未处理旧请求、同ID重推、多参与者A1/B2/A3、其他bot只做背景、权限隔离、NO_REPLY及投递失败。再用获准飞书会话验证实际模型输入与客户端结果。

## 不做

不使用关键词过滤问候、不写消息重要性分类器、不按固定年龄丢消息、不增加定时合并等待、不逐条制造历史user回合、不修改pi会话历史、不把群里所有人提升为owner。

## 尚待实现时确认的技术边界

需核实可用的原生时间顺序字段与并列顺序、现有上下文预算如何同时覆盖背景及待处理项、已完成事件与飞书原生消息的关联。平台不可见/缺权限历史明确报告；不承诺恢复平台没有返回的内容。尚未确认65分钟迟到的SDK/平台原因，不以推测增加重连/重试机制。


## 已批准实施细化

使用既有turn上下文贡献channel-feishu.conversation，不新增Channel/SDK上下文接口；插件新增conversation.ts负责有界历史准备，index.ts注册。history.ts增加反向分页选项及连续发送者分批；core仅补原始时间/消息ID可选字段与呈现。生产main的owner/observer显式选择上下文，现有输入/处理/投递状态继续各自归属。历史预算及线程范围不足必须展示，不能暗中截断后声称完整。当前实现路径还包括对应最小回归、插件README、spec/01通用可选时间字段及上述设计条款。
