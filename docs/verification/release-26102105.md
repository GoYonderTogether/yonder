## 3 项失败的原因

1. `background.test.ts`（15 秒让出，上界 18000ms）：整套并行时本机负载平均数上升到约 100，实测 18803ms。单独运行通过。曾试图把命令改成 30 秒并放宽上界，但 `process wait` 的默认等待上限使之失败，已撤销，保持原用例。**真实回归整套并行时请限制并发**（`npx vitest run --maxWorkers=4`），否则时间类用例会抖动。
2. `delegation-results.test.ts`（D46 既有用例）：模型在第二个子任务里回复了 `DELEGATION_DONE` 而不是要求的随机令牌，属于模型输出不确定；单独重跑通过。
3. `effort.test.ts`（本轮新增）：对“无 admin 调用者被拒绝”的断言曾假设模型在报错后不再重试；这次模型去掉 `effort` 重试了一次普通委派，断言失败。内核行为没有问题（工具报 admin 错误，未创建带 effort 的委派）。已把断言改为：该会话转录里有 admin 错误结果，且之后创建的委派都不带 `effort` 字段；单独重跑通过。

## 0.2.26102104 上线时发现的问题（已修复或已记录）

1. **自动升级被拒绝**：生产机当时装的是本地候选版（`localCandidate: true`，来源 tag 为本地验收标签）。GitHub 监听器检测到新 Release 后返回 `failed-or-unknown`：“Installed executable/service/home boundary does not match configured update target”，没有升级。改用受支持的手动路径 `yonder update --to v0.2.26102104` 完成，之后安装来源是正式 tag，后续自动升级应恢复；**这条自动升级链在正式来源上的恢复尚未再次实测**。
2. **升级后首次启动崩溃一次**：更新进程在控制接口未就绪时走离线路径，把被占满事件循环的启动中服务的锁判为陈旧并接管，服务随后以 `ECOMPROMISED` 退出，launchd 重启后恢复；停机约 3 分钟。当时本机负载约 30（并行测试），服务启动用了约 80–100 秒（空 home 同版本启动数秒，说明慢在带 87MB 状态库的初始化与负载）。已在 #12 修复。**启动耗时与该负载的关系只是推断，未单独复现。**
3. 同一时刻 `release.update-result` 被记为 `failed-or-unknown`、`verified:false`，原因是上面的时序；事后 `yonder service info` 显示 `0.2.26102104 / 8fd59d1 / ready`。
