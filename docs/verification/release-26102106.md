## generation 失败诊断

分别从 `653c4bb`（已发布 05）与 `6cc74c3` 创建 `/private/tmp` 隔离 worktree，每棵执行 `npm ci`、`npm run build`，再以原始提示运行三次：

```sh
YONDER_KEEP_TEST_HOME=1 YONDER_TEST_REAL=1 YONDER_TEST_AUTH=<repo>/.yonder/auth.json \
  npx vitest run --exclude '**/dist/**' packages/core/src/kernel/input-queue.test.ts -t generation
```

仅增加 finally 中的现场写入，不改变行为与断言；每次另有 2 个非 generation 用例被筛选跳过。

| 版本 / 次序 | 通过 / 失败 / 跳过 | 实际非空 final |
|---|---|---|
| `653c4bb` / 1 | 0 / 1 / 2 | `Input A, Input B, Input C.` |
| `653c4bb` / 2 | 0 / 1 / 2 | `A, B, C` |
| `653c4bb` / 3 | 1 / 0 / 2 | `QUEUE_MERGED_A_B_C` |
| `6cc74c3` / 1 | 1 / 0 / 2 | `QUEUE_MERGED_A_B_C` |
| `6cc74c3` / 2 | 1 / 0 / 2 | `QUEUE_MERGED_A_B_C` |
| `6cc74c3` / 3 | 1 / 0 / 2 | `QUEUE_MERGED_A_B_C` |

六次均只有 **1 个 run.end，inputs 长度 3，status done**；packets 均含一个空 final（被插话中止的生成）和上表非空 final，message.out 文本与之相符。失败不是缺少投递，也不是 5 秒后仍在等模型；模型已经用 final 送达其他文字。旧版两次复现，故分类为 **既有、模型输出相关**，没有证据表明由 `6cc74c3` 引入。

根因是 B 要求回答输入标签，C 要求精确令牌，两条队列消息竞争最终格式。最小修正：B、C 均要求同一令牌，不延长超时，不删除或放宽断言。保留一个运行合并三条输入、状态 done、最终令牌投递、旧回答不投递、工具只调用一次及中断工具报错的验证。证据写入移入 finally，使失败时也可保留。两棵临时 worktree 已移除；六份原始 evidence.json 另存操作机 `diagnostic-evidence/`。
