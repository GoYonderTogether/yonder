# 工具、MCP、技能、记忆与上下文资产

## 工具与 MCP 要指导行动

一个工具说明至少要让 Agent 明白它操作什么、何时使用、关键引用从哪里取得、返回代表什么，以及必要的后续衔接。按真实工具复杂度取舍，不强制每个工具都用同一份长模板。

- 名字或领域术语不能替代概念解释。例如“会话通知”可能只记录程序消息，并不唤醒模型，也不证明用户已读；说明中应消除这种实际误用。
- 参数约束交 schema，描述补充语义与用法。先查得真实对象再修改的接口要说明查找入口；会产生外部副作用的接口要说明结果不明时如何核实。
- 区分 MCP 服务端暴露本系统、MCP 客户端调用外部服务、宿主桥接工具。接上一个服务不代表全部工具都可用，原生能力、工具发现与权限仍有效。
- 返回结果简短、结构化，保留真实 ID、状态、产物与可行动错误。需要时说明“已接纳/已运行/已投递”分别是什么，不能统一返回含糊的成功。
- 不把整部产品手册或重复示例塞入每个工具描述；共用概念在合适上下文讲一次，特定工具补实际差别。反过来，不能为了短把工具变成没有解释的名字和参数堆。

新增说明前读调用方、执行实现、结果处理和真实误用证据。使用成熟仓库的接口作为参考时，核对执行环境、权限、重试与取消前提，不能复制专有 API 名称后声称 Yonder 支持。

## 资产的操作不只有追加

| 操作 | 适用判断 |
|---|---|
| 保存 | 新的、已确认且有持续价值的事实或方法，保留范围与来源 |
| 合并 | 同一责任与适用范围的重复内容，处理冲突并保留必要出处 |
| 编辑 | 事实变化、用户纠正、术语或步骤过时，修旧结论及引用 |
| 拆分 | 多种独立场景导致选择困难、无关内容总被加载 |
| 删除 | 已确认错误、无保留需要且获准删除的内容，先查调用与归属 |
| 归档 | 仍需追溯但已不适用的历史，让它退出活跃索引和常驻上下文 |
| 检索 | 任务需要时定位材料及证据，不让保存自动变成每轮全文加载 |

技能、记忆、工具清单和 MCP 接入不是相同载体：文本可以合并，工具需要保持公开接口兼容；删除说明不等于卸载服务，卸载不等于删除用户数据。先查选择来源、调用者与资产所有者，再做与目标相称的整理，不创造统一数据库或万能清理器。

用户明确要求保留全部原文时，原始档案完整保存，活跃索引、摘要和选择加载另行整理。用户反馈形成窄而准确的修订，不每次新增一条全局禁令。临时要求、推断的情绪和虚构设定不混入永久事实。

## 复用与拆分的分寸

改专业流程先找既有 skill 与项目实现，缺能力先找成熟工具或插件；只有当前缺口才支持新增。通用编码、修复、普通接入不因出现两次就必须变 skill。需要专门质量标准、领域工艺或稳定流程时，再形成能够按需发现的技能。

每项长期文本说明适用对象、触发范围与事实来源，选择入口清楚，细节按需读。长短服从职责：内置理念与常驻规则不能因追求缓存而丢掉必需语义；单工具引导不承担全体系思想教育。

清理应由真实使用、过时、冲突和检索困难触发，不每轮运行大扫除或自评。先完成当前任务；有具体收益时，在授权与预算内维护，必要时向用户说明影响。不要因用户情绪激烈就删除边界、全部资料或原设定。
