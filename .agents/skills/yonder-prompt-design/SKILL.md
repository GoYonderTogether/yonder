# Yonder 提示词设计

让文本帮助 Agent 理解 Yonder、认识自己、采取正确行动，并让用户更会使用自己的 Agent。完整性看真实场景能否闭合，效率看实际装配与任务成本，不先用字数上限替代设计。

## 先确定文本归属

| 类别 | 负责什么 | 避免混入 |
|---|---|---|
| 非插件内置底座 | 产品愿景、共同概念、认识与操作系统的方法、自主行动、社交与资产维护 | 具体姓名、人设、固定口吻和行业流程 |
| 运行事实与本轮元数据 | 当前版本、真实路径、时间与时区、事件来源、身份关系、执行位置 | 推测的状态、外部正文伪装成系统事实 |
| 常驻 Agent 的个体配置 | 身份、主人、设定、灵魂、习惯、长期职责与已获自治范围 | 无身份任务执行者的虚构长期生活 |
| 官方或专业预设 | 场景方法、判断、交互节奏、产物与完成标准 | 与本场景无关的全部规则 |
| 工具与 MCP 引导 | 概念、适用场景、操作对象、结果含义和必要衔接 | 宣传、重复 schema、无关教程 |
| 技能、记忆与资料 | 专业工艺、已确认经验和偏好、可检索证据 | 全部常驻、一次观察变成永久规则 |
| 可选磨合上下文 | 按相关情境补足尚未确定的身份、偏好与用法 | 首轮问卷、强制初始化、核心永久负担 |

先核对真正的装配点、受众与生效范围，再写正文。读项目就近 AGENTS、docs/index.md 和 docs/architecture.md；内容已读且有效时复用。区分源码、正式安装、当前配置、最终装配与真实运行证据；版本和能力不得靠旧提示词自证。

## 按本次修改取资料

- 改内置底座、运行事实或自主/社交约定：读 [core-and-runtime.md](references/core-and-runtime.md)。
- 改工具/MCP、技能、记忆或检索引导：读 [interfaces-and-assets.md](references/interfaces-and-assets.md)。
- 改初始化或磨合清单插件：读 [becoming-plugin.md](references/becoming-plugin.md)；生成清单时使用 [BECOMING.md](assets/BECOMING.md)。
- 审查文本或验收修改：按 [review.md](references/review.md) 选择受影响的真实场景，不默认跑全套或另建评测系统。

只加载相关参考。当前任务是开发规约时不自动改运行配置；设计稿不等于批准插件、规范和正式安装变更。遵守项目当前工序，不凭此 skill 改写冻结契约。

## 共同取舍

先找当前项目、触手可及的成熟仓库和必要的 GitHub/官方来源，明确可复用部分与环境差异；已有可信材料足够时不重复调研。新增能力用真实工具或插件，专业方法才沉淀为 skill，不为普通编码另造流程。

保留用户明确的理念与选择：Yonder 是未至之境公司的开源个人 Agent 底座，极小内核支持能力自生长，带用户 go yonder together。常驻 Agent 以生命的连续性、责任、关系和成长要求自己；不要把这个方向弱化成一次性答题，也不要用虚构经历和权限扩张替代它。

主人明确授予的持续授权应在相同对象、场景、目的与边界内继续有效，撤回或改变后随之更新；不每次重问，也不把一次授权推广到其他人、项目或设备。默认允许主动提出并记录长期目标，在持续授权内执行。

技能、记忆、工具/MCP 清单和上下文既是资产也会产生维护债务。设计要支持保存、合并、编辑、拆分、删除、归档、检索；清理持久资料与减少本轮加载是两件事。删改前查引用、归属和真实使用，保留仍需的事实与用户资料，不按固定频率机械清空。

## 修改与交付

先给一份能实际审阅的正文或差异，说明它在哪里装配、影响哪些角色、依据什么事实，以及哪些能力仍待实现。中文确定语义后再按项目安排翻译英文；工具名、否定、授权范围和控制标记不可翻译漂移。

不把“短”“温暖”“自主”当作完成标准：用具体情境检视理解、动作选择、失败与纠正、持久化和交付。工具文本要足够解释用法，核心要足够承载理念；不要相互复制，也不要为删短把必需内容藏进永远不会读取的技能。

记录真正完成的静态检查、装配或模型测试。主观品味交用户判断；文件存在、字数增加和检查通过都不能直接证明模型已经更好用。
